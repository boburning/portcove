# Catalog and Library filters

`CatalogFilters` presents platforms, Core's host platform, release channels, all
eight setup methods, selected Library membership, observed installation attention
and update candidates using `evaluateCatalogQuery`. Alternatives within a group
are OR; groups are AND against one Core browsing context. Machine `beta` is
displayed as Preview. Browsing never grants action permission or qualification.

App supplies one accepted generation-bound workspace snapshot and canonical
selected library identity consistently to result filtering, option counts and
detail inspection. Core owns its ephemeral browsing projection, including host,
route/platform/channel/setup method, retained instance and definition digests.
Retained manifest/SQLite reads occur during snapshot refresh, under a shared
32 MiB allowance and cooperative 250 ms stop between reads. Individual I/O and
parsing have no hard 250 ms deadline. Construction preflights repeated fields,
caps contexts at 8192 and serialized output at 4 MiB, and streams input hashes.
Missing or bounded-out projection cannot prove a coherent local combination.
In my library means an active managed installation or registered external runtime;
previous or staged-only records do not establish membership. Membership does not
assert readiness or tested installed-platform compatibility. Installed platform
comes from retained metadata; legacy absence stays unknown. A declared Linux
setup cannot satisfy Linux plus In my library for a Windows installation. An
occupied setup remains a declaration, not an absent-library context. Missing library context is
unavailable, never Not in my library; a confirmed empty snapshot is distinct.
Restored membership selections remain visible/removable while context is absent.
Library keeps its existing view narrowing: Not in my library can legitimately
have zero matches there without switching sections or relaxing the query.

App supplies the complete accepted catalog/listing/pending union for Discover facet
counts and comparisons; text search narrows matching results after query evaluation.
This keeps Single/Multiple tied to total distinct port identities. Library supplies
its existing membership-scoped candidates before editable groups. Library additionally narrows results using the existing
`filterPorts` All/Ready/Needs attention semantics, independent of the declared
query. Ready includes staged installations; Needs attention retains unknown,
repair, source, BIOS, runtime and blocked readiness. Readiness remains an
independent observed status narrowing, not platform qualification. Core remains
the installation/readiness authority.

PortBrowser applies the session Favorites predicate before option counts.
Platform/channel/membership/setup counts exclude their own choices and retain readiness plus
all other groups. Readiness counts retain the declared query and exclude the
readiness selection. Counts are distinct ports, may overlap and need not sum.
Each positive combination shares one context. Unknown retained fields produce
unavailable results/counts when they could change the answer; they never become
false zeros. Matching context identities accompany results into detail inspection.
Detail choices expire on workspace binding change and never select a different
build silently. Game-file observations join only the exact route, platform,
channel, definition and installed-instance digests. Selected zero-count options remain removable. Missing candidate snapshots or
active Favorites without confirmed choices show unavailable, not numeric zero.
Accepted cached snapshots remain usable during refresh failure under the
existing refresh notice. App remounts the workspace by library generation and
its existing snapshot hook discards obsolete async results.

Filtering performs no I/O, scanning, planning or lifecycle mutation. Unfiltered
lists keep unknown declared facts. Launch/install revalidation is unchanged.

The existing per-library browsing preference key is retained. Wrapper version 2
adds an independent Library readiness string; compatible version 1 inputs are
migrated on read. Legacy ready/setup move to readiness with an unrestricted
declared query; legacy channels retain the same evaluator meaning. Structured
queries retain their version and values. Unknown readiness stays visible and
constrains Library results until explicit correction. Unsupported or unavailable
queries stay held for explicit reset, including malformed values. Established
extra predicates are preserved on edits and visibly called out for reset.
Future/unreadable preference records retain their bytes and the existing explicit
retry/reset guards; no second preference store or durable authority is introduced.

Reset Library filters resets only the declared query. All resets only readiness.
Reset view clears search, query, readiness, session Favorites and selected collection. Clear filters retains search; inline Clear search retains filters.
Catalog resets retain their prior behavior. Section/root isolation, details/back,
restart, existing sort and in-session scroll/selection context are retained.
The shared button and inline panel controls provide keyboard dismissal and trigger focus
return; removing a focused chip returns focus to Filters. Repeated selections use
functional updates. Closing a panel keeps its already-applied selections.

The contextual projection and its consumers are owned by #1550. Source and
selected fixture evidence do not by themselves complete that owner or establish
native, physical-controller, human or game execution qualification.

## Observed installation attention

The Installation attention group exposes exact Core reasons for identity-matched
active managed or registered external installations from the same accepted
selected-library snapshot. Missing game files, Missing BIOS and Missing runtime
consume `missing_source`, `missing_bios` and `missing_runtime`; Repair needed
consumes `invalid_installation`. Finish setup consumes `pending_setup` or
`preparation_required` independently of `launchable`. Changed and unreadable
observations never become missing-file matches. Stage-only, absent or malformed
readiness and inconsistent port/installation identities establish no positive
reason; unfiltered browsing retains them.

Attention alternatives are OR, other groups and existing Library readiness are
AND. Distinct counts exclude the attention group's own selections; selected zero
and unavailable choices remain removable. Version-1 queries without attention
keep their semantics; unknown restored reasons remain unresolved for reset.
These observations do not describe complete compatible source sets, install
eligibility or a ready installation for a declared platform. They perform no I/O
or lifecycle authorization. [#1551's final completion receipt](https://github.com/boburning/portcove/issues/1551#issuecomment-6111474268)
records the delivered route-bound game-file filtering boundary; the finite
observed update predicates are documented below.

## Observed update candidates

Available at last check and Matching update staged consume Core's saved
`update_available` decision in the accepted selected-library snapshot. The shared
`observedUpdateCandidate` helper also supplies the card's available-update badge.
It validates the expected port/status/active/check, selected channel, installed
version/full artifact and field-wise runtime before the recorded candidate's
channel/version/artifact/required runtime. A verified staged record must match
that candidate; zero candidate size retains Core's unspecified-size convention.
Available excludes its matching staged candidate. Other downloaded versions do
not satisfy Matching update staged. The existing generic downloaded badge still
reports a retained download independently of this exact candidate predicate.

Readiness remains independent: a playable installation can have a staged update,
and a runtime-only candidate can retain the same game version/artifact. These
are observations at the last matching check, not a newly checked/latest release,
installation eligibility or execution authorization. Missing, malformed or
obsolete observations establish neither positive choice nor up-to-date. Unknown
entries stay unfiltered; absent library context is unavailable, confirmed empty
is zero. Query version 1 keeps compatible legacy/absent-group semantics; unknown
restored choices remain actionable through existing reset/correction. The local
predicates carry no private path or installation identity in the persisted query.
No check, scan, hash, network, plan or mutation occurs while matching. Complete
route-bound game-file acceptance remains with #1551.

## Game-file observation history

The feature-owned `useGameFileObservation<T>` shares the two explicit checks' request
lifetime. Each owner retains its request construction, guards and complete-scope
acceptance. Context epochs hide obsolete results, errors, operation controls and
history immediately, including A→B→A. A distinct attempt identity owns events and
settlement, so a settled request cannot replace a newer cancellation target.
Exclusion starts before reading library identity and lasts until actual settlement,
even after context changes or a cancellation acknowledgment. An obsolete held
identity read never starts a Core query. A valid completion after cancellation was
requested is accepted normally; only an authoritative cancelled rejection shows
that outcome.

An accepted observation means the response passed its scope-specific contract,
including Files missing, Needs checking, No files to add in Portcove and Unavailable
context. It does not mean compatible files were found. Current classifications and
matching-evidence maps are separate from immutable metadata: Core's observation
and expiry timestamps, the exact requested port/route/platform/channel list and
its original monotonic deadline. Retry immediately clears current usability while
retaining that metadata. Failure or actual cancellation leaves it informational;
new acceptance replaces it. Sticky expiry remains bound to the original accepted
record through retries, failures and clock changes. Expired history never revives.

`GameFileObservationSummary` presents an exact localized Core time in a machine-readable
`<time>`, with Last checked for usable results and Previous check for history. The
current status explains checking, failure, cancellation or expiry. Time and scope
support the existing result and check control. First attempts have meaningful
pending/failure/cancellation status without inventing a previous check.

Catalog history reaches details independently of current classification and
matching-context branches and only for ports in its recorded request. Labels come
from that record, never the detail selection. Complete catalog means the requested
catalog ports for the recorded route/platform/channel, not every combination.
History supplies no classifications, counts, complete-set or matching-build
evidence, and no registration/setup/install/update/launch permission. All existing
definition and installation-instance matching checks still apply to current data.
Expired catalog history directs the player to Filters → Check game-file filters.

Catalog history survives details/back and Catalog/Library navigation within the
mounted workspace and unchanged observation context. Library/generation, catalog,
sources, statuses, browsing binding or requested selection changes clear it; a
remounted workspace starts empty. Independent selected-route history ends when
its detail owner unmounts. Neither history is persisted or cached. Navigation,
filtering, presentation, expiry and ordinary rerenders start no inspection. The
two existing check controls remain the only inspection actions.

Original-game/source-edition metadata is descriptive and authorable through the
catalog. Unknown identities never merge by equal titles. Reviewed systems are
independent of target OS, and originalSystems/portOptions extend the same query
evaluator. Results label known game groups separately from ungrouped projects.
Identity chip colors are optional metadata decoration, never readiness feedback.
