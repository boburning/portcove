# November player copy reconciliation

Issue [#4412](https://github.com/boburning/portcove/issues/4412) tracks this
finite audit follow-up within [#200](https://github.com/boburning/portcove/issues/200).
The audit compared `dcbec47a96a5098bac325ed8e1c6b69cedf0accc`. Reconciliation
started from remote main `b0a9224b32593ee54c0c265afecaf05caec55b66`. The
changes to setup routes, update controls, CLI imports and Vite+ after the audit
were inspected before editing. Related prior issues #4198, #4207 and #4229
remain closed. The earlier notice hiding, numeric catalog schema validation,
settings labels and managed recovery behavior were retained.

The audit and its JSON findings were available. For the catalog inventory, we
read both baseline blobs directly from Git and verified their SHA-256 hashes
against the audit receipts. We screened all 1,424 listings (1,216 guides) and
288 operational definitions on both revisions. The inventory ZIP itself was
unavailable. Screening recovered the 14 listing IDs with “execution intent”,
the 521 matching experimental status notices and the repeated 87/85 setup
paragraphs. A further occurrence was in an operational preparation note.

The change distinguishes the 87-entry kit cohort, whose shared paragraphs,
Windows/Linux platforms, step roles and title-specific middle steps were checked,
from 24 individually selected catalog records that changed. The cohort retains
each exact original-file step and its platform prerequisites. Render96 was
also read as evidence for shared saves. Most catalog entries received screening
only. The entries with long summaries or the same experimental notice are
review candidates. We consolidated repeated status and evidence in selected
guides where the duplication was clear. The remaining notices require their
own context before further editing.

“Changed” records an implementation in this candidate. The verification column
names the test or evidence route, including cases inherited from existing
tests. CI and review determine delivery. Tests using a browser fixture or an
inspection of upstream source cannot establish native or gameplay behavior.

The new authored catalog rule rejects “execution intent” in browse summaries,
guide actions and warnings, and legacy setup text shown without a guide.
Technical references retain exact terms. The negative fixture failed against
the earlier authoring validator because it accepted the bad copy. The same
test passed after the check was added and accepted a technical reference with
the phrase as well as literal filenames. The pinned generated listing also failed the new
first-warning assertion before the guide change and passed it after regeneration. The Desktop rule targets the two
observed blanket save-separation claims. Required validation uses the existing
catalog, frontend and Rust contexts. Ordinary Playnite changes also select the
compiled Windows reference-client contract.

Contextual review still owns warning relevance, real recovery destinations,
translated meaning, keyboard flow and comprehension. The Second Hunt evidence covers the inspected source, the guide before setup and the Desktop warning before attached-copy Play. Binary cleanup and gameplay were not reproduced. Browser fixtures and the Playnite contract
runner do not establish native UI comprehension. English is the supported
locale. The changed messages here were inline, authored or backend text.
