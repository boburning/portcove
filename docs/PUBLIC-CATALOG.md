# Generated public catalog

`scripts/public-catalog.mts` builds read-only pages. It uses the generated
directory of projects and the definitions Portcove uses to manage ports.
Use the pages to browse and compare projects.

Generate a development preview in a new output directory:

```sh
node scripts/public-catalog.mts \
  --listings crates/portcove-core/catalog/listings.json \
  --catalog crates/portcove-core/catalog/catalog.json \
  --revision "$(git rev-parse HEAD)" \
  --observed-at "$(date -u +%Y-%m-%dT%H:%M:%SZ)" \
  --output work/public-catalog-preview
```

Serve that directory with a local static HTTP server. The output has a catalog
index, a compact `search-index.json`, stable `games/<reviewed-game-id>/index.html`
pages and `projects/<implementation-id>/index.html` pages for ungrouped projects.
Implementations of a reviewed game have separate sections and comparison rows.
Matching titles alone never group projects. Source editions remain separate from
target platforms. A shared runtime never combines different original games.

Search and filters use the generated local index. The pinned Node runtime
removes types from checked `search.ts` to produce `search.js`. Publication needs
no extra packages. The renderer fingerprint identifies the TypeScript source,
CSS, and generator.

If JavaScript is off or the index fails to load, the HTML still contains every
link. If the index fails, the page explains the failure and turns off filters
that need it. You can still use the page if some implementation details are
missing or unknown.

The projection copies only an explicit public field allowlist: descriptions,
reviewed game identities and editions, upstream links, target platforms, optional
method/dependency evidence, setup steps, optional reference titles and instructions
under **Setup notes**, limitations and declared scoped
check platforms. It excludes private maintenance data, user library records,
local paths, credentials, arbitrary extra fields and artwork. External text is
escaped and only HTTPS links without credentials are rendered. Input reads,
search downloads, generated file counts and aggregate bytes have finite bounds.
Output goes through a new staging directory; an existing result is preserved.

## Development and published delivery

Every current page is explicitly a **development catalog**. The generator records
the exact source revision, input digests and observation time. A captured catalog
is not a new upstream verification, a gameplay result or a published delivery.
Availability is labeled an upstream claim; release existence alone cannot become
a playable package. Definition presence is labeled a development integration.
Published delivery remains **Not checked**. No app handoff URL is manufactured.

The existing `.github/workflows/catalog-publish.yml` is the only publisher.
It selects the newest CI-green main commit, runs the existing isolated role
signers, assembles the TUF repository without keys, then generates these pages
from that same checked-out commit into `repository/browse/`. The normal guarded
replacement of `gh-pages/catalog/` therefore includes the pages. No key,
environment, root, workflow trigger, review gate or signer authority changes.
The stable entry URL is `catalog/browse/index.html` below the existing Pages site.

The unchanged decision compares both current public data digests and the fixed
renderer/CSS/script digest with retained `browse/inputs.json`. Unrelated main
commits and observation-clock changes do not rewrite an identical snapshot.
Renewal re-renders unchanged validated data with the original capture revision
and time, preserving identical output bytes. It never copies prior HTML or
scripts. Missing, malformed or unreadable prior enrichment requests fresh output;
a failed new build stops before replacing the existing published catalog.

The prepare stage keeps the complete previous tree digest, including browsing,
as its concurrency preimage. Signer inputs copy the previous TUF repository
without `browse/`; the capture is retained separately for deterministic renewal.
Readback compares the actual Pages timestamp, browse index and input identity
with this run's generated bytes. A Pages propagation timeout remains an explicit
warning, not verified delivery. The site still labels all operational facts as
development and published route availability as not checked: a published web page
is not a published executable definition or client acceptance.
