#### Reviewed source policies

`sourcePolicies` in `daily-discovery-sources.mts` names the reviewed sources
outside normal automated collection. Each is reported whenever it is read, with
its role, reason and reconsideration condition, and neither role makes a run's
coverage partial.

- **Reference: PCGamingWiki.** The unofficial-ports page yields no structured
  rows, so it is captured at most every 30 days as one fingerprint of the
  page's content without comments, scripts or whitespace
  (`snapshot_kind: reference-capture`); a failed capture is retried next run. A changed page enters manual review
  once; the reviewer records the wiki revision and changed rows and verifies
  candidate leads against primary upstreams. On 2026-11-18 and 2026-11-23 the
  page, MediaWiki `parse`/`query` and Cargo `cargoquery` endpoints answered
  HTTP 403 from a Cloudflare edge block. Promote it to collection once a
  supported structured surface answers and yields rows.
- **Suspended: PortForge.** Only the provider's answer about the repository
  (HTTP 403, 404, 410 or 451) keeps the suspension; quota, credential, server
  and network failures are ordinary failures that keep the run partial. `zamiba/portforge-mediaitems` answered HTTP 404 to
  the 2026-11-23 audit; Git reported authentication required and raw files 404,
  so private, renamed and deleted are indistinguishable. A winget installer
  redirect ties the earlier `portforge` publisher to `zamiba`; no successor
  repository is attributable. Each run makes one metadata probe and records
  its HTTP status, error class, environment and the last good tree clock.
  The retained checkpoint and provenance stay. Full collection resumes when the
  same repository reads again under its own name. A repository answering under
  another name is a successor: it is reported (`successor`) and needs review
  before it becomes the source, and a surviving fork never replaces it.

A failed reviewed-source read records the request URL, error class, HTTP status
and execution environment (`github-actions` or `local`). A runtime access
failure is not evidence that a source retired or a project was removed. A read
stopped by a run boundary (budget, quota, rate limit, deadline, cancellation)
is a resumable `partial` read marked `deferred`, not an inaccessible source. Quiver
records its failing feed request; its evidence is Portcove's own API request,
and `tgeorgiadis/quiver-launcher` is named as the publisher's client of the same
API.

The additional recomp.board source reads the published
`https://recomp.fyi/feed.xml` Atom feed, not the restricted bulk table. It validates
the full currently published feed and retains exact upstream links, event clocks
and provenance. A feed gap retains positive leads without advancing its
successful clock; an expired entry is not evidence of project deletion.

### Curated list leads

`collect` first reads four public curated lists through the bounded discovery
transport: the Decomp Buddy finds feed
(`https://tanookistudios.com/decomp-buddy/finds.json`, 8 MiB cap), portsdr.com
(`port-card` Repository links, 4 MiB cap) and the Alexbeav PS1 catalog
(`catalog-data.js`, read as text and never executed, 1 MiB cap), and RecompSoftware's
`data/projects/games.json` (8 MiB cap). RecompSoftware first resolves `main` to
an immutable commit, then reads that exact revision; its successful clock retains
the source URL, revision and SHA-256 of received content. Decomp Buddy's
published catalog is read too, but it leaves out projects without a desktop
download, so the finds feed and the two original lists stay inputs.

Further structured sources follow the same contract (shapes verified live on
2026-11-23; each feed answers conditional requests):

- Decomp Buddy's `catalog.json` (schema 1; 4,148 entries on 2026-11-23): one
  entry per game, so a multi-game repository keeps one claim per game. Each
  claim keeps the console, desktop platforms, release, Decomp Buddy's
  completeness label, a `takedown` status and lineage: its `sources` become
  `origin` (`portsdr`, `alexbeav-psx`, `decomp-buddy-finds` or the named list).
  An unknown schema or a count that disagrees with the entries fails the read.
- Decomp Buddy's `waiting.json`: projects that have no Windows, macOS or Linux
  download yet (status `waiting`). Its `hidden` rows are Decomp Buddy's own
  rejections and count as excluded.
- decomp.fun's hourly `v1/projects.json` and per-game `v1/games.json`. Every
  project keeps its own identity; a game's leading project never suppresses
  another (`status` is `leader` or `alternate-of:<leader>`). Each claim keeps
  the game slot and its matching progress in tenths (sources publish
  percentages, so 0.99 is under one percent), so a small percentage move is not
  a research change.
- unbaked's weekly `api/additions.json` (every project the registry gained in its
  published weeks, a rolling seven-week window) and its complete registry
  baseline (below).
- PortMaster's `ports.json`. Its index names no upstream field, so only GitHub,
  GitLab and Codeberg links in its own descriptions and instructions are hints;
  links to PortMaster's own repositories are not upstreams, and its handheld ARM

- Open Source Game Clones' `games/*.yaml` at one exact revision, read through one
  directory listing and one raw read per file and parsed as plain data without
  aliases. Only `remake` and `official` entries are native-port leads; clones,
  similar games and tools are counted as excluded and never hinted. The source
  repository's provider ID is pinned on the first complete read and must match
  on every later read; a different repository at that path is a failed read
  that keeps the last good clock.

`relation: distribution`, the `channel` and the channel's pin, so paths,

packaging script is executed. The ScummVM engine is never hinted through a
channel (the ScummVM expansion stays excluded).

- **Luxtorpeda** (`https://luxtorpeda.org/packagessniper_v2.json`, the index the
  publisher generates from `codeberg.org/luxtorpeda/packages`, which replaced

  tools, and Proton-only packages (a `uses_proton` notice) are excluded; on
  2026-11-23 the index named 190 engines and 252 games, giving 124 native
  upstreams and 56 exclusions.
- **Mac Source Ports** (`https://www.macsourceports.com/meta.json`). Each macOS
  build's upstream project is a hint; its architecture is the claim's target.
  A build Mac Source Ports produced itself is `separately-built`; a build the
  project published itself is `upstream-build`. Mac Source Ports' own forks
  are never upstreams and are excluded. Game associations live only in the
  site's bundled script and are not read.
- **Batocera** (`package/batocera/ports` in `batocera-linux/batocera.linux`) and
  **RetroPie** (`scriptmodules/ports` in `RetroPie/RetroPie-Setup`) are
  repository-directory baselines. The default branch is resolved to an exact
  revision with the repository's provider ID pinned, and the directory is
  listed. Batocera is listed to the package level (44 package definitions on
  2026-11-23); deeper sub-packages are mods and game data for a port, outside
  native-port scope. A file name outside the item form is counted and skipped. Each definition file is an item whose
  fingerprint is its blob, so only new and changed definitions, and any
  unread for thirty days, are read at that revision. A Batocera `<PKG>_SITE`
  names the upstream (a download route built from make variables keeps the
  project path before them) and `<PKG>_VERSION` is Batocera's pin. A RetroPie
  `rp_module_repo` and further `gitPullOrClone` repositories name upstreams;
  only a commit is a pin, since a branch moves and a `:function` resolves at
  install time. RecompLauncher values on a host it does not name, or a GitHub
  value that is not exactly `owner/name`, are never mapped to GitHub. Both
  directories also hold software outside native-port scope; research
  classifies each upstream.

#### unbaked registry baseline

`api/games.json` lists every registry game (7,723 on 2026-11-23) but no
repositories; each row links its per-game record. The `unbaked-registry` list
is a resumable baseline. Like the directory baselines, it runs only in
unattended collection, after every other list and hint resolution; interactive
runners take its results from the shared store:

1. The inventory is read daily as a conditional request. Each row is
   fingerprinted without its star count, which moves daily.
2. Every due game record is read while the run's budget allows: never-read
   games first, then games whose row changed, then the longest unread, and any
   game unread for thirty days (reconciliation). A failed record waits a day.
3. Each record's projects merge as soon as it is read and are saved every 25
   records, so an interrupted run keeps them and resumes from the next due game.
4. The list's complete clock moves only once every game has a record read for
   its current row by the current parser; a game waiting out a failed read
   keeps the list incomplete. Its scope is the inventory read it describes.

A failed inventory read waits two days, as a list does. A parser change makes
every record due again. A record's first read is discovery: its claims never
mark a repository as changed, even when another record of the same source
already named it, so a shared engine is not sent to research by the baseline.
A later read of that record whose claims differ is a change.

A game without public code keeps `candidate-without-public-code` on its
projects' claims and is counted in the summary as an unresolved research
candidate. A project's official site stands in when it has no repository;
general tools are excluded. A game leaving the inventory drops its progress,
never its hints. Additions remain the incremental feed, and ordinary upstream
watches follow changes to known projects; additions are not a complete change
log.

Each list is read at most once per run, again after its refresh interval
(seven days by default), and only while twenty-two requests (the research
reserve plus four possible redirects) and the list cap plus 1 MiB remain. A
malformed, oversized, count-mismatched or failed list keeps its prior complete
clock and hints, records its failed attempt, waits two days before another read
and is recorded as a partial note. Parser diagnostics never copy list bytes. A
failure anywhere in this step leaves the rest of `collect` running.

Lists that answer conditional requests (the Decomp Buddy feeds, decomp.fun and
unbaked) are read daily with the validators of their retained read. A 304
records `unchanged_at` and keeps the retained entries and hints without a new
parse. Validators apply only to a copy parsed by the list's current parser
version and only when the configured URL answered without a redirect, so a
parser change or a redirect always reads the source in full. A source that sent
no validators is read on the default interval instead.
Each list clock records the bytes its read transferred. A list is admitted by
its expected size (its last read, or the size observed when it was configured,
plus a quarter), not by its cap. Its cap, about four times the observed size,
only guards against a runaway response; per-item records have their own 1 MiB
cap. Every read is also bounded by the run's byte budget and the physical read
ceiling (an eighth of the machine's memory, at most 512 MiB).

HTTPS GitHub and Codeberg `owner/name` and GitLab project paths (up to four
group segments) and a truncated inert title are retained in `leads.json` as
resolvable hints, with the lists that named them, the list whose read created
them (`discovered_by`) and first/last observation clocks. An official project
URL on any other host (a SourceForge project root, a self-hosted forge or an
independent site) is retained as a `web` hint in the `unsupported-host` state.
It is taken up when a provider adapter supports its host or an attributed
source names a resolvable repository for the project; it is never researched
as a GitHub repository. A web location ignores the scheme and fragment and keeps
the query; a SourceForge route or project site becomes its project root. Video,
social, chat, storefront, encyclopedia, archive, donation, link-shortening and
aggregator pages, and GitHub, GitLab or Codeberg routes other than a
repository, are not upstreams. A `www.` forge host is the forge itself; a
non-HTTPS repository link is never turned into a mapping.
Name-only entries are counted, never mapped. A list no longer naming a
repository is not deletion evidence. Hints are not leads: they grant no
admission, support, catalog or planning facts, and list text is never followed
as instructions. Retired list ids stay readable in retained state.

After list collection, at most eight uncovered GitHub hints per run, newest
first, receive one primary `repos/{owner}/{name}` metadata read while eighteen
requests remain. A hint is covered when a canonical issue upstream, reviewed
catalog lineage URL or a retained lead's current repository path names it;
unchanged covered hints are never read. Historical lead aliases do not cover a hint,
because another repository can reuse an old path. Only an answer for the listed
path joins the ordinary lead queue, through the same immutable-ID rules as
search results. The discovery SDK refuses redirects, so a renamed or transferred
path, HTTP 404/410 and HTTP 403/451 access blocks mark only that hint
unavailable for thirty days for manual research at its new location. An answer
for another path or a path owned by another retained ID marks it as a conflict
for thirty days; malformed metadata or another typed client answer for that
path is a failed read retried after one day. Admission, budget, quota,
rate-limit, deadline, credential (HTTP 401), server (HTTP 5xx), retry-exhaustion
and scope refusals, and any unclassified error, stop resolution and mark no hint.
A list read refused for budget or quota stays due; other list failures wait.
RecompSoftware retains each source slug, subject, category, method, status,
targets, original-copy flag and latest-release claim within its repository hint.
Shared repositories receive one metadata read while keeping their independent
source-entry associations. These are external claims, including category
`games`; none establishes a reviewed game identity or playable runtime. Upstream
summaries and code are not copied. No repository/data license was found in the
reviewed `e981757f31fdb58b85e546069cf303daac56cc61` tree, so these parsers are
independent implementations and retained facts require primary-source research.

The already consumed review snapshot is the bootstrap baseline. If a first

A failed or partial read retains last-good content and clocks. Identical claims

A source's claims about a repository are attributed source entries. Beyond the
RecompSoftware fields, an entry may carry its relation (`implementation`,
`distribution` or `mirror`), every game the source associates, a progress band

Resolved leads record `external_lists` provenance and then follow the unchanged

- `hints`: hints it names;
- `discovered`: hints its read created;
- `originated`: hints whose claims name it as their origin, or that it

- `platform_claims`, `pending_changes`, `unresolved_hosts` and its hints by

quiet-rotation lead coverage. Hints live in `leads.json` and its recovery copy

### Ecosystem continuity and burst signals

Every appended search family uses the existing persisted fixed-window/page
continuation, 48-hour overlap, search ceiling splits and resource-admitted
allowance. Rotation resumes across runs; a completed page is not an ecosystem
completeness claim. Weekly canonical rechecks and manual focused sweeps remain

identity join.

helpers and frameworks do not create independent port issues. These reviewed
identity fields participate in the candidate fingerprint and are checked again
after the fresh pre-mutation inventory.

## Unattended collection

The [maintenance workflow](../.github/workflows/maintenance-inventory.yml) runs
deterministic discovery collection in its `discover` job on the existing daily
04:47 UTC schedule, after the `collect` job applies migrations. It uses no
terminal, personal checkout, model or Roadmap credential, and adds no new
schedule. `node scripts/discovery-worker.mts collect` runs the same collectors as
the interactive `collect` operation (`scripts/discovery-collection.mts`): curated
list hints, bounded lead-search families with their fixed windows, overlap and
continuation, and the reviewed source collectors. GitHub access is read-only and
the client refuses every mutation.

State lives in the [maintenance store](MAINTENANCE-STORE.md#discovery-collection),
not in a local file. The worker takes a fenced lease and a database acquisition
ticket before any external read, then commits the lead continuation, the new
positive provider observations and watch changes together. It commits every
half lease, which also renews the lease, and always commits its last state. A
crash before a commit replays those pages; identical observations are stored
once. A stale or expired worker, or one from before a restore, cannot commit.

Unattended collection applies no per-run counts. It has no research or delivery
reserve and no fixed request profile:

- every due curated-list hint is resolved, the longest-waiting first;
- every pending lead's releases are rechecked, the never-checked and then the
  longest-unchecked first;
- lead searches continue through every family and continuation.

Only physical limits stop a run. These are observed provider quota and
Retry-After, half the runner's free disk for retained responses, the job's
deadline (GitHub's hosted-job maximum, less time to commit the final state), and
database transfer.

A run is a sequence of passes. Each pass holds its own transfer admission,
sized from the stored state and the previous pass, plus its own lease and
attempt. Neon meters only what the database sends to the client, so a pass's
transfer is its responses: the acquire read of the state and lead records, and
each commit's short acknowledgement. What a commit sends is recorded as
`sent_bytes` but is not charged. A later pass of the same run offers the revision, generation and definition it
committed, with the attempt that committed it. The store omits the state only
when it still holds exactly that revision and that attempt is the scope's latest
committing attempt. The pass then reuses its own copy and lead records instead
of reading them again. Attempt ids are random, so another writer's commit, a
restore or a branched store that reached the same revision through other commits
does not match, and the pass reads the stored state in full. While a pass runs,
it also keeps the retained copy, so unattended collection holds up to two
copies of its state, each within the runner bound below.
A pass ends when its work is done, when provider quota runs out,
when its admitted transfer could no longer cover the next commit's and the
final one's responses, or when its admission window or the job deadline nears. When quota or transfer
ended a productive pass, the worker holds nothing while it waits for the
quota reset, then starts a new pass. A pass that changed no state is not
repeated. Passes share the run's start, so a release already checked or a
search window already completed in this run is not redone. Fair ordering means
sustained new hints cannot starve older work. The interactive runner keeps its
bounded slices and reserves for in-run research, and its 32 MiB lead-state
envelope, which also bounds its local journal files. Unattended collection keeps
lead records as database rows, read back in pages, and bounds its in-memory
lead state, source checkpoint and research progress by the runner: a quarter of
its memory, within the longest string the runtime can serialize. Each commit sends the state document with only the records that
changed.

Unattended runs also backfill history. Once forward searches, release rechecks
and the reviewed source collectors have run, each search family has a second
window that moves backward from where
its forward coverage starts, a year at a time, to 2008-01-01 (GitHub's launch;
no repository is older). A window past GitHub's 1,000-result search ceiling
halves itself, as forward windows do, and the next window steps back from the
original start. A piece that still cannot be narrowed is recorded as capped,
never as covered, and the rest of its window continues. A page whose membership
moves or that GitHub marks incomplete keeps its identities and is recollected
on a later run. Families take turns. When a family's sweep
reaches the epoch, a repair sweep starts again from the top in a later run, so a
repository that became searchable late, through a metadata or topic change,
visibility or delayed indexing, is still found. Backfill progress is part of the
collector state, so it resumes across passes and runs.

Canonical ownership is `unknown` in this path. The worker reads catalog lineage
but not the Roadmap inventory. A retained observation is a lead, not intake,
identity resolution or admission; the hosted bridge and its receipts still own
canonical intake. Budget, quota, deadline and cancellation end a run as `partial`
with its continuation intact. An inaccessible source is recorded as such and
never as absence. Exit code 75 means deferred: inactive store, lease held,
resource admission or missing credential. Any other failed database commit stops
collection and fails the job at the last committed page, so a store error is
never recorded as a source outcome. `result.json` lists every pass with its
outcome, `committed.state_bytes` and transfer.

Before bulk community-list work, each admitted collector pass gives retained
release probes an early turn. It stops starting probes when they consume a
quarter of the pass's initial request, byte or time budget. Each request remains
subject to the existing admission and persistence paths, and one response can
cross the early byte or time threshold. The collector then continues normal
collection and later release checks for newly found leads. Never-checked and
longest-unchecked leads go first. Probes use GitHub's immutable repository ID.
An inaccessible or malformed response records a retry clock and preserves the
last successful package observation. A lead keeps its dated observations across
a refresh and can be probed again in a later run. Provider-wide quota,
authentication and transport failures still use the existing boundaries.

The natural maintenance run can prepare listing additions from retained
positive release watches. The collector keeps the observed release ID, response
digest and exact repository path with the lead. The next run can reconsider
that candidate after interrupted preparation or an unavailable release probe.
A complete sampled response replaces the previous observation. A renamed
repository needs a new observation at its verified path before preparation.
The maintenance store keeps the preview's starting point and upper
repository ID. Each admitted run starts after the preceding run's first
candidate, so a full preparation window still gives the next candidate
a turn. Newly observed higher IDs join the next sweep.
The run exports the committed discovery generation,
revision, release ID and digest of the observed release response for each
selected repository. The preview runs only for a handoff whose digest matches
the current collection result. The batch preparer checks the local catalog and
revalidates public repository identity through the read-only GitHub credential.
It records unresolved candidates and
provider and deadline deferrals alongside successful proposals. When scope
verification finds an eligible addition, the preparer acquires the official
Core reader and validates the listing projection. The scheduler retains the
handoff, evidence, completion report, proposed records and any validated
append-only patch in the discovery artifact. The aggregate preview files stay
on the runner. A release hint is a reason to assess a candidate. Canonical
admission and signed publication use their separate decision paths.

A lead whose recent releases have no uploaded desktop asset gets a
`no-native-package` watch (`waiting`). When a later run sees uploaded desktop
assets for the same provider ID, the watch becomes `due` in a new episode. This
needs no title-specific code, issue or allowlist. Due watches are pending

Automatic executor dispatch stays disabled under
[#8570](https://github.com/boburning/portcove/issues/8570), so the status

`node scripts/discovery-worker.mts status` writes a read-only export

The status export also derives `lead_reconciliation` directly from stored lead,
upstream observation and intake checkpoint rows. Cohorts count scope/repository

intake and prepared checkpoints are separate flags; several candidates for one

necessarily new, and a matched repository may contain another game or edition.
Use current canonical owner and primary game evidence through the existing intake

create issues, grant support, enable dispatch or introduce a new scheduler.

### Local runner on the shared store

When `PORTCOVE_MAINTENANCE_DATABASE_URL` is set for a local `run`, the shared
store owns lead collection for that runner, and `plan` reports
`lead_collection: "shared-store"`. Its `collect` operation then:

1. Reads the stored leads without a lease. The read holds its own transfer
   admission, sized from the stored state. If the stored revision moves while it
   reads, it reads again.
2. Keeps this runner's research on top of the stored leads. A local record keeps
   its status, research, disposition and review clock only while it names the
   same repository at the same revision. A changed upstream takes the stored
   record, which queues it for review again. Leads from the session's own
   `search` operations stay local, unless the store holds the same path under
   another provider ID.
3. Skips the curated lists and lead searches, which the store has already
   collected and backfilled. The reviewed sources are still collected locally,
   because their checkpoint carries this runner's research queue.

The journal and the lead summary record the stored revision, record count and
bytes read (`lead_collection`). The store's searches satisfy the run's search
requirement, so `recheck` and `finish` can complete without local searches. A
scope filled only by `import-local` also counts, although no collector has
searched it since; run `discovery-worker.mts collect` once after an import. If
the store is empty, local collection runs as before. If the store is
unavailable or its admission is deferred, local collection also runs as before,
and a partial note records why. `plan` reports the configured mode; a fallback
shows only in the run.

Each read reserves its whole payload: the admission meters 70% of a
reservation, so the reservation is the stored state and records divided by 0.7,
plus 1 MiB. A read that sees a commit is repeated, each time under its own
admission.

`daily-discovery.mts` removes the store URL and the Neon meter credential from
its environment before its first Git command and hands them to the session
alone, so no child process receives them. In
this mode the local lead copy is bounded by the machine's memory rather than by
the 32 MiB local envelope. A `leads.json` written this way may then exceed the
envelope of a later run without the store; set the variable again to continue.

`node scripts/discovery-worker.mts collect` can also run on a local machine and
add collection capacity to the same store. It takes the lease like the scheduled
job and records a `local:` runner identity. Without the variable, the local
runner keeps its own `work/daily-discovery/` cursors.

original request/byte/time allowance; insufficient capacity or further churn
stops without accepting the abandoned view. Charged large-inventory fixtures
cover both completion within the remaining allowance and refusal before a
replacement that cannot fit.
`canonical-baseline.json`, `project-items.json`, `checkpoint.json`,
`active-run.json` and `runs/<run-id>/` retain identities, evidence and recovery.
They are collection caches, never independent planning or support authority.

HTTP response bodies, redirects and failed attempts share the same ledger.
The bounded worker streams at most 2 MiB into retained response buffers and
drains before the foreground process can finish. Provider backoff is persisted.
An uncertain worker failure receives a conservative charge. Git fetch is a
separate metadata Git operation with a finite 60-second timeout; its time counts
in the session deadline, while its transport bytes are outside the API-body
ledger. Its command disables commit-graph writing and automatic maintenance,
including inherited settings: shared-repository housekeeping must not consume
the discovery fetch budget. Existing graphs remain available for reads, and
this command does not change Git configuration or schedule maintenance.
Final receipts disclose actual charged requests/bytes and gaps. Fixture tests,
manual runs and actual scheduled runs are different evidence scopes. Keep
#2100 validating until three actual scheduled receipts have been evaluated.

Discovery state uses an exclusive sibling file followed by atomic replacement.
On Windows, replacement alone waits at most one second (25 ms intervals, at most
41 attempts) for `EPERM`, `EACCES` or `EBUSY`. Readers without delete sharing can
cause these errors; the code does not infer which process holds the file.
The same prepared bytes are retried, with no unlink/truncate fallback. Persistent
failure retains the old target and pending sibling. File creation, API requests,
and whole runs are never retried by this mechanism. Local contention time counts
toward the existing session deadline; it neither resets nor extends that deadline.
