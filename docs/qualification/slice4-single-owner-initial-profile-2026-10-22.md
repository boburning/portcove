## Implemented boundary

Release-tools has a closed InitialRootProfile with legacy-two-of-three-v1 and single-owner-one-of-one-v1 variants. Existing ceremony and context configurations default to the legacy variant. The single-owner variant must be explicitly selected in trusted configuration using initial_root_profile; it is never inferred from a Root document's threshold, key count or signatures. Unknown profiles refuse during strict configuration parsing. The selected profile participates in the complete context/configuration bytes already retained by the maintained signers and source closure.

Single-owner preparation requires exactly one Root public key and three separate top-level Targets/Snapshot/Timestamp keys. Each role uses threshold one and distinct Ed25519 material; existing application releases/preview/stable delegates and catalog definitions/policy delegates stay separate. Proposal, sole-key signing, keyless finalization, initial Targets, application aggregate and isolated signing/assembly, catalog signing/assembly and read-only verification all check their explicitly configured profile. Legacy entrypoints without the new field retain the two-signature requirement. No generic minimum-threshold relaxation or alternate signature verifier is introduced.

Root v1 ceremony, exact reviewed canonical-body digest, current generation window, maximum 365-day Root expiration, consistent snapshots, separate role keys, input/link bounds, no-clobber outputs, actual signature verification and keyless assembly remain. Root signing still reads only one key per invocation. The single-owner signer refuses a second signing attempt once its quorum exists; finalization reads no private key. Targets custody and automatic renewal are separate implementation work, not completed by recognizing this Root shape.

Core selects the new initial catalog profile through a fixed reviewed-source constant beside its immutable include_bytes anchor. Public API arguments, environment and downloaded definitions cannot select it. The checked-in anchor is still null. The existing fixture-only legacy route retains its profile for prior evidence. Exact compiled/stored anchor matching, stale-plan refusal, replay floors, existing policy/admission/curated history and lost-response idempotence are unchanged. Neither a different one-key root nor a new one-key root over an existing legacy library can replace its authority. Existing Tough rotation/replay behavior is unchanged; a real earlier published anchor requires its authenticated history and applicable old/new rotation process, not a fresh initialization claim.
