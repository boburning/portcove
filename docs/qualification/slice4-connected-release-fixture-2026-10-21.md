# Connected disposable release qualification

This #534 preparation connects maintained byte and crypto implementations in one
nonproduction test. It grants no production, native, semantic or hosted release
authority. The six packages are deliberately inert fixture bytes, compatibility
and eligibility fields are declared fixture data, and the provider is controlled.
No installer, application, model, live Release or Pages operation runs.

## Connected path

`scripts/release-connected-fixture.test.mts` performs these operations in order:

1. Use the real Git version preparer on an inert workspace. Verify exactly four
   version-authority files change, the source checkout stays at its original
   commit, and the resulting commit/tree binds the six-package beta aggregate.
   The assembler still reports `original_compiler: null` and unevaluated release
   authorization.
2. Generate one disposable Tauri key. Sign the exact aggregate NSIS/AppImage
   bytes through pinned Tauri 2.12.2 and independently verify them through the
   maintained Rust tool. Changed payload bytes refuse. Remove the private payload
   key before record or metadata consumers run.
3. Reuse the existing disposable Root/offline Targets/five-online-key fixture,
   binding its public payload registry to the actual generated public key.
   Assemble an authenticated empty predecessor, reconstruct nonempty Preview
   release records from the actual signed bytes, then run five separate one-key
   Rust workers and keyless Tough assembly. A changed envelope signature and an
   attempted Stable promotion refuse. Fixture results cannot pass the hosted
   actual-publication getters.
4. Drive maintained draft/create/upload/publish transitions against an explicit
   controlled provider. Every transition recollects the complete Release/tag/
   asset inventory; uploaded byte readback equals the original aggregate and
   detached signatures. No production token, provider request or authorization
   receipt is created.
5. Compose the complete site, preserve exact independent catalog bytes, and
   exercise the fixed public HTTPS readback against the controlled transport.
   Feed the actual nonempty public repository to the Rust/Tough renewal adapter,
   sign all five renewed roles and verify immutable target/history preservation.
6. Use the existing real Git coordinator journal and bounded renewal operation.
   Lose the response after the controlled provider replaces its complete site.
   Refuse a second effect while pending, recollect the exact public bytes, record
   the existing readback and published-metadata transition, then refuse stale
   replay. The upload count remains exactly one and no candidate is allocated.

This exercises the existing local persistence/readback seams. It does not mint
an actual hosted executor, exercise remote journal CAS, or substitute controlled
readback for future authenticated Releases/Pages service observations. Full
native execution, semantic judgment, compiler/SPDX acceptance and the ordinary
public V0-to-V1 journey remain separate obligations.

## Observed local result

The resource-admitted Windows run passed one connected test with zero skips in
44.2 seconds. Host-capacity queue time was 122.9 seconds and is separate from
execution. It reused the preserved maintained Rust binary with SHA-256
`ba6eb7cbb60cbefa26014834091aa70cff1b59f4f8be9e561272956984cdcbc7`.
The actual signer addon and Node bytes were checked by the maintained signer.
The source log is `work/slice4/connected-release-sixth.log`.

Retained earlier failures were fixture setup/expectation defects: missing local
package policy, omitted internal prior-repository manifest, overlapping renewal
work root, and an expected-error expression that did not match the maintained
pending-operation refusal. An intervening capacity-queued run was cancelled
before payload execution; no foreign process was signalled. Product guards and
assertions remained enabled throughout.
