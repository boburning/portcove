# Trusted coordinator continuation and initial empty application feed

Owner: [#534](https://github.com/boburning/portcove/issues/534). This is implementation
and disposable-fixture evidence. No production key, App, protected ref, workflow,
Pages configuration or execution grant is created by this delivery.

`scripts/release-coordinator-driver.mts` connects the existing remote journal
recovery, complete publication inventory, planner, sparse version preparation,
prepared-object transport, capacity executor and exact prepared-tag dispatch.
It recovers before reading new opportunity facts. A neutral request binds the
actual publication/source baseline and accumulated changes without inventing a
classification. The default wake discovers the exact accepted independent Check
and persisted classification automatically; missing, duplicate, contradictory,
changed or unauthenticated observations remain held. Actual negative Check
dispositions can retire the exact request through the same journal and bounded
repair counters. A transport or startup failure is not a semantic disposition.

The `persist-request` reviewed-inputs mode discovers the accepted Check for the
outstanding journal request and uses the existing classification writer CAS.
It requires its own fixed writer source/OIDC admission, ratified producer roles,
fresh isolated protection evidence and an unchanged request checkpoint before
mutation. It does not accept a manually selected opportunity or Check ID.
The dedicated journal credential remains separate from provider/dispatch and
classification credentials. Parser results and injected transports confer no
authority.

Initial application metadata uses an explicit
`application-tuf-initial-bootstrap` descriptor. Its setup-plan and observed
initial-site preimage digests are facts bound into the same journal, not proof
that setup was authorized or that every historical URL was absent. The descriptor
fixes the externally ratified Root, offline Targets, public payload-key registry,
empty records and initial online versions/expirations. The public Rust context
requires exactly one of `previous_repository` and `initial_bootstrap`.
Initial records must be empty; no previous feed, candidate, source classification
or positive capacity observation is fabricated. Each routine role job still
loads only its own key; assembly remains keyless and verifies all role envelopes
with the maintained Tough stack. Root and top-level Targets custody stay offline.

A schema-2 checkpoint may have `opportunity: null` only in this explicit initial
bootstrap state, with no active candidate or reserved versions. Its plan has no
invented source or classification authority. The bootstrap operation uses the
existing pending-before-effect remote CAS, invocation nonce, executor identity,
bounded receipts and readback recovery. A seed requires the matching settled
effect and actual derived publication facts; a nonnull published metadata state
permanently closes this initial path. Existing candidate identity is preserved.
Authenticating those publication facts and the initial site remains the fixed
caller's responsibility, not a consequence of a descriptor hash.

Retained local checks include four Rust bootstrap tests, two real-Git null
opportunity journal cases, one real-Git/injected-provider remote custody case,
29 pure coordinator/capacity contracts including the four legacy plan digests,
and 120 target-composition inventory/routing tests. They establish the exercised
fixture behavior only. The public-only disposable bootstrap fixture export
contains context, anchors, payload registry, empty records and signed envelopes;
it excludes job configs and private keys. Earlier failed compile, lint and fixture
attempts remain retained under `work/role-signing`.

Remaining integration is explicit: default metadata-renewal scheduling and final
candidate completion must consume actual authenticated public feed/full-site
readback and the matching settled journal operation. Release presence alone
does not finish a candidate. The automatic semantic service, first-site setup,
actual provider controls and protected execution still require their separate
implementation/qualification and the consolidated owner grant. This document
does not declare the production path complete.
