# Slice 4 native stage and payload signing join preparation

Owner: [#534](https://github.com/boburning/portcove/issues/534). This preparation
connects the actual native Check consumer to acquisition and the payload role.
It grants no signing, credential, native account or publication authority.
The held workflow fragments remain outside `.github/workflows`.

The fixed payload caller loads the protected, digest-bound authority inventory
through `requireControllerReleaseAuthorities("payload")`. The seven configured
App roles must be distinct. Candidate JSON and returned Checks cannot select
the native issuer, host, account, minimum engine, producer source or harness.
The only dynamic native inputs are two exact
`{platform_label, check_id, invocation_id}` locators. Candidate source, tree,
run, attempt, immutable platform artifact and updater-package bytes come from
the same private acquisition. Windows NSIS and Linux AppImage reports cannot
qualify the unchanged full package profile.

Actual default-provider native receipts retain their private runtime brand and
are rechecked before the continuation. Imported or injected reports cannot enter
it. All applicable compiler, SPDX, security, classification, semantic, pause,
capacity, reservation and source checks remain required. The authenticated tool
artifact supplies the exact compiler source closure. Pre-sign eligibility is
called `eligible-for-payload-signing`; it is distinct from publication admission
and retains the post-sign compatible-update, rollback and journal obligations.
Publication additionally retains its explicit signed-context join hold until
that connection is implemented. Full public V0-to-V1 acceptance remains separate.

The actual positive continuation retains the privately recovered bare
coordinator repository, actual native receipts and signed SPDX receipt separately
from public facts. A serialized context cannot appoint any of them. The payload
role authenticates its own numeric OIDC job identity under
`production-payload-signing`, then uses the existing capacity executor and
dedicated journal transport. Its stable operation destination is
`github-actions:boburning/portcove:VERSION:payload-signatures`.
The existing remote pending checkpoint must be established before the key
channel opens. The operation covers signing, immutable output handoff and
remote settlement. A partial or ambiguous result remains pending for existing
coordinator readback/recovery; it does not automatically repeat key use.

Every protected continuation round obtains a new nonce-bound observation.
Actual native, SPDX and tool custody are rechecked before signing. Capacity-only
reads preserve the existing operation's own pending-ownership checks; subsequent
reservation checks use the actual pending checkpoint rather than the original
pre-effect checkpoint. Payload subprocesses share a fixed total phase deadline
with thirty seconds reserved under the proposed ten-minute job ceiling.

The fixed upload handoff publishes only public signatures and their exact input
binding. A reviewed upload step must upload `signature-handoff/output/*` once,
with seven-day retention and no overwrite, then atomically create
`signature-handoff/uploaded.json` containing only numeric `artifact_id` and the
opaque ZIP `sha256`. That file supplies a locator, not custody. The process
independently reads the current controller attempt, exact numeric producer job
and artifact before and after bounded opaque download. Complete raw ZIP
preflight, CRC, exact inventory, member hashes and retained-file equality must
all pass before the existing journal can settle the handoff.

The private prepared-signature getter rechecks actual native/SPDX/tool and
signature custody and exposes the exact settlement and immutable output
readback. It does not turn those provider facts into cross-job attestation or
publication eligibility. The existing custom-predicate attestation, complete
TUF role wrappers and private record/context consumer join remain implementation
work. The historical held payload fragment does not yet supply the new output
upload protocol and cannot be activated as this complete role job.

The six signing executor profiles are `payload-signing`, `tuf-releases`,
`tuf-preview`, `tuf-stable`, `tuf-snapshot` and `tuf-timestamp`, matching their
existing fixed job names and separate environments. Each TUF role can hand off
only `github-actions:boburning/portcove:VERSION:tuf-ROLE-envelope`. Neither a
payload nor a metadata executor can dispatch Release, publish a Release, deploy
Pages or use another role's output scope. Metadata-only renewal remains explicit
and uses the existing authenticated unchanged-feed descriptor.

Local focused validation currently covers 80 passing contracts, including
actual-default/injected-provider separation, the two native stages, immutable
package association, all signing-role identities/scopes, exhausted deadlines,
malformed upload locators, complete ZIP/member checks, changed local output,
provider drift and bounded waiting with retained public partial output. This
is fixture and source evidence. No actual native capture, protected key,
controller signing run, attested signing artifact or production execution has
been observed by this preparation. Existing failures and prior evidence remain
retained under `work/slice4`.
