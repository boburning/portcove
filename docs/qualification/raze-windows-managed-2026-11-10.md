# Raze Windows managed route

Seven cataloged titles share one official upstream player, ZDoom Raze: Blood, Duke Nukem 3D, NAM, PowerSlave / Exhumed, Redneck Rampage, Shadow Warrior and World War II GI. Each gains a managed Windows x86-64 route from the same official `Raze-<version>-windows.zip`. Portcove downloads, verifies, installs, launches and updates the player. The player still finds or is told where the player's own original game files are, in its own game selection; Portcove does not authenticate, copy or move originals. Each title is a separate Portcove installation with its own Raze configuration, with no automatic title dispatch. The macOS and Linux guidance in each listing is unchanged: upstream publishes a macOS ZIP and no Linux package in the selected release, so those stay player-managed.

The inspected stable release 1.11.0 Windows asset is `Raze-1.11.0b-windows.zip`, 18,364,194 bytes, SHA-256 `16718c28d8d6853b418d467af0354b8c2a21f6c1bebb1686ef2da9896caac2e5` (computed locally from the downloaded bytes; the release API reported no digest). It holds eight entries with no wrapper folder and no links: `raze.exe`, `raze.pk3`, `soundfonts/raze.sf2` and four DLLs. The selector pieces `Raze-` and `-windows.zip` match this asset only, not the separate `Raze-1.11.0-windows-pdb.7z`, and carry no version, so a compatible later release needs no catalog edit.

Raze's Windows portable mode (`source/common/platform/win32/i_specialpaths.cpp`) is keyed on a file named `raze_portable.ini` beside `raze.exe`. When it is present and writable outside Program Files, the configuration is that same file, saves go to `Save/`, screenshots to `Screenshots/`, demos to `Demos/` and documents to the program folder; `autoexec.cfg` is read from there. The node cache and the application data folder stay under the Windows local application data folder, outside the managed runtime. Because the marker file is also the player's configuration, Core's new `portable_marker_file` declaration (native capability 19) creates it only when missing and never truncates it, and each record declares `raze_portable.ini`, `Save`, `Screenshots`, `Demos` and `autoexec.cfg` as persistent paths. Existing normal-profile locations under Documents and Saved Games are not imported. Older readers refuse these definitions.

These are static package and source observations. The player was not run, no original game files were available, and nothing observed whether Raze writes further files beside the executable in portable mode beyond those named by its path code, so unclaimed files there remain a risk until a Windows run. Gameplay, saves, original detection and the player's own caches are unobserved. [Official release](https://github.com/ZDoom/Raze/releases/tag/1.11.0), [portable path source](https://github.com/ZDoom/Raze/blob/master/source/common/platform/win32/i_specialpaths.cpp).

GZDoom (Doom / GZDoom, issue #1824) uses the same shared engine path code (`src/common/platform/win32/i_specialpaths.cpp` in `ZDoom/gzdoom`) and gains the same managed Windows route from the official `gzdoom-<version>-windows.zip` (inspected g4.14.2, `gzdoom-4-14-2-windows.zip`, 21,879,627 bytes, SHA-256 `6d01c5bb48610cebfa9dfd0b7705a1e20bfd56032a74484ac256d8c4e3c51bee`, computed locally). It is flat with 15 entries and no links: `gzdoom.exe`, `gzdoom.pk3`, three more PK3 files, a soundfont, two bank files and three DLLs. The selector pieces `gzdoom-` and `-windows.zip` match only that asset, not the `-windows-pdb.7z` or the DEB and macOS packages. Its portable marker is `gzdoom_portable.ini`, with `Save/`, `Screenshots/` and `Demos/` and the program folder for documents, and it declares the same five persistent paths. As for Raze, the player was not run, no IWAD was available, and the macOS and Linux guidance is unchanged. UZDoom, which already has other managed routes, was not touched.
