# Catalog complete-site continuation preparation

This is source and controlled-connection evidence. It does not establish an
appointed production catalog publisher, actual GitHub OIDC/provider behavior,
key custody, a successful Tough invocation, catalog semantic acceptance or public
publication. The protected catalog configuration and its future grant remain
separate from application release appointments.

`runFixedCatalogSiteConfiguration` accepts exactly:

```json
{
  "mode": "catalog",
  "identity": "existing AssemblerIdentityExpectation object",
  "tools": {
    "artifact": "existing ControllerToolArtifactExpected object",
    "bundle": { "artifact_id": 1, "sha256": "64 lowercase hexadecimal characters" }
  },
  "context": "existing SigningContextArtifactExpected object for catalog context",
  "roles": [
    "CatalogRoleArtifactExpected: purpose catalog, role definitions",
    "CatalogRoleArtifactExpected: purpose catalog, role policy",
    "CatalogRoleArtifactExpected: purpose catalog, role snapshot",
    "CatalogRoleArtifactExpected: purpose catalog, role timestamp"
  ]
}
```

The strings above describe existing strict nested schemas; they are not runnable
values or additional accepted forms. The callable authenticates the actual fixed
site job, receives tools/context/four role artifacts, runs the actual keyless
assembler and rechecks its private receipt. It acquires the current remote
coordinator journal and validates the exact catalog descriptor and both component
pins. It uses the existing globally exclusive artifact-upload intent and existing
site artifact/transport, then the existing sole Pages writer/status/readback path.
The returned decision is `catalog-site-published`, with the durable checkpoint and
site generation. The affected catalog record and global cursor advance together;
application bytes and its original publication record are preserved.

The initial catalog-only whole-site branch requires an explicit optional
`catalog.public_source.initial_site_preimage` locator `{path,bytes,sha256}` in the
protected catalog authority configuration. It is a distinct JSON pin, at most
128 KiB, and changes the complete authority configuration digest. The existing
Root/Targets appointments remain the only public key appointments. Initial journal
`catalog_initialization` must match that configuration, source commit/tree, Root,
setup plan and preimage. The reader authenticates the complete Git tree and three
raw blobs, then independently observes configured provider state and the same four
fixed public routes returning 404. It repeats this fresh bracket before the sole
POST. Historical owner/user-site absence stays historical. Existing catalog or
application sites use actual whole-site custody instead. Application bootstrap
after catalog still needs its separately explicit setup-preimage variant.

GET-only lost-handoff recovery uses an actual named coordinator recovery assembly,
the original settled catalog Pages expectation, an independent read of the
already-public generation and the existing terminal original-job checks. It does
not compose another generation, upload or POST again. It rechecks preserved
application inventory/root and marker ancestry before the same atomic recorder.
The public helper is `recoverActualCatalogSitePublication`; imported assembly,
deployment and executor objects cannot enter it.
