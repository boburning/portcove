## Runtime, data and preservation

The checked runtime `main` calls `RuntimeMain`; ordinary game execution remains
there until worker/renderer shutdown and return. The direct no-argument route
fits existing selected-process supervision. This is source fitting, not
binary/source attestation or an observed game run.

Portable discovery searches from the executable parent through four ancestors
for `portable.txt`; the found root's `UserData` owns Config.toml, NAND, Cache and
Logs. A typical layout is `<portable>/Install/Base/WiiCompiled.exe` alongside
`<portable>/portable.txt` and `<portable>/UserData`. Preserve the whole tree and
marker. Moving Base alone or changing the marker can change the active profile.

Otherwise Windows uses known-folder LocalAppData/WiiCompiled, with a fallback to
WiiCompiled beneath the current working directory if that known folder fails.
Multiple installations can share that profile. Relative configured paths resolve
from the Config.toml **parent**, never from Base CWD. Preserve all actual custom
`nand_root`, `dvd_root`, overlays, GameAssets and original files too.

Upstream may seed missing bootstrap files in a configured NAND. Startup also
prunes entries older than four days from its Logs folder, which contains per-run
console and crash evidence. Preserve required diagnostics before Play. The guide
states these effects; registration preservation does not guarantee that upstream
will retain every external file. No new sandbox, writer ownership, migration,
cross-profile compatibility or immutable data boundary is claimed.
