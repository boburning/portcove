## Runtime, data and legacy boundary

Capability 4 locates the runtime and its declared data at the selected player's
directory, so ordinary changes to the outer versioned wrapper do not require
definition edits. The existing Core normalization/materialization contract
checks the canonical original independently of the runtime archive. Core's
portable marker keeps normal data local to that player.

Declared data includes settings and recovery siblings, saves, mods/mod config,
achievements, race/rider/character preferences, custom music, complete local
race packs and their importer jobs/backups, and the verified original copy.
The authored record carries the exact paths. Current declared data, including
data created before first Play, participates in shared backup, compatible
replacement, recovery and runtime rollback. Runtime logs remain disposable;
modified package files and unknown additions still hold unsafe operations.
Rollback carries current data and does not rewind progress or guarantee older
software can read it.

Optional course/texture/character imports stay deliberate upstream features.
Portcove does not automatically discover and run DirectStart or import helpers.
Close the player and any importer before replacement/backup. Custom external
course-pack paths, including `RR64_PRIVATE_COURSE_PACK`, remain outside managed
backups. Imported/user mod code is not authenticated by preservation.

The historical definition used v1.4.3-specific persistent coordinates. The new
catalog entry does not reinterpret that captured contract or promise a safe
automatic namespace migration. Existing copies keep their files, current Play
and retained recovery contract; incompatible updates remain held. The supported
transition remains unfinished work, not a seamless migration or a newly approved
product deferral. A separately prepared/customized external copy keeps its own
upstream update owner and requires explicit saved launch details and Play.
