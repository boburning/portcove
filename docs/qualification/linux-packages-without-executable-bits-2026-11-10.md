# Linux packages without executable bits

Three managed Linux x86-64 routes could not install because the official upstream archive stores the program without an executable bit: OpenJazz (`openjazz-linux-glibc2.35-x86_64.zip`, `OpenJazz` inside `OJ-a1626f4/`), Paperboat (`Paperboat-Mulberry-Delta-Linux.zip`, the `Paperboat.AppImage`) and Perfect Dark (`pd-x86_64-linux.tar.gz`, `pd.x86_64` and its regional variants, from the rolling `ci-dev-build`). I extracted the real archives with Core's managed extraction and resolved the declared executable with Core's own resolver on the embedded definitions. Each extracted correctly and then stopped at "declared executable is not executable on this Unix host": every entry is stored with mode 644. Core treats a program's executable bit as the archive's own statement of intent and never invents execute permission for a binary the publisher did not mark, which protects executable trust. The one reviewed exception, OpenMoHAA, enables execution for exactly its launcher and engine after checking their binary headers. These three routes have no such declaration.

The fresh definitions therefore stop offering Linux for these three. Their Windows routes, and installed copies under retained definitions, are unchanged. This change does not weaken the executable-trust rule. Reconsider when upstream publishes the program with its executable bit set (a packaging fix that costs the publisher one `chmod` before archiving), or when Core adds a reviewed, declared mechanism that grants execution to a named program only after verifying it is a binary for the platform, which could serve all three routes and replace OpenMoHAA's one-off step. No Linux player was executed. A first copy of the Perfect Dark archive was corrupted locally by my scratch storage and produced a misleading tar error; the finding above uses a copy whose SHA-256 matches the publisher's digest.
