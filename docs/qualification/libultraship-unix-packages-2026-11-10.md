# libultraship Unix package routes

Ship of Harkinian, 2Ship2Harkinian, Lighthouse and SpaghettiKart declared managed Linux and Mac routes that were never qualified (only Windows x86-64 was, as the closure comments on [#58](https://github.com/boburning/portcove/issues/58), [#59](https://github.com/boburning/portcove/issues/59), [#60](https://github.com/boburning/portcove/issues/60) and [#62](https://github.com/boburning/portcove/issues/62) state). I extracted each package with Core's managed extraction and resolved the declared executable with Core's own declared-executable resolver, using the embedded catalog's real definition. Before this change all nine tested routes ended with "none of the declared executable hints were found": the 2Ship Mac, Shipwright Mac, Lighthouse Mac and Ghostship Mac packages, the 2Ship Linux, SpaghettiKart Linux and Ghostship Linux packages, and both SpaghettiKart Mac packages.

The causes are package facts. The 2Ship, SpaghettiKart and Ghostship Linux ZIPs each hold one AppImage with its executable bit set (`2ship.appimage`, `spaghetti.appimage`, `ghostship.appimage`) plus data files; Lighthouse publishes a raw `lighthouse.appimage` asset. The SpaghettiKart Mac ZIPs hold a bare `Spaghettify` Mach-O, a separate arm64 and x86_64 package. The Shipwright, 2Ship, Lighthouse and Ghostship Mac ZIPs hold only a `.dmg` disk image and a readme.

This change names the true executables in the hints (`2ship.appimage`, `spaghetti.appimage`, `lighthouse.appimage`, `Spaghettify`). After it, the 2Ship Linux and the three SpaghettiKart routes resolve their executable against the real packages. For the three DMG-only Mac routes (Shipwright, 2Ship2Harkinian, Lighthouse), Core cannot open a disk image, so the fresh definitions stop offering a managed Mac install and their listings give the same upstream handoff the BattleShip record uses: get the disk image, copy the application, register it with Choose existing installation, and keep its data separate. I did not open any disk image, so the app bundle layout, executable name and data location of those Mac apps are unverified, and the guide says so. Installed copies keep their retained definitions.

Not changed: Ghostship and Starship, which keep their separate prepared-route status under [#53](https://github.com/boburning/portcove/issues/53) and [#61](https://github.com/boburning/portcove/issues/61). Ghostship's Linux AppImage and Mac disk image have the same shapes and need the same hints and handoff when its owner route allows. Reconsider the Mac handoffs when Core can extract disk images safely, or upstream publishes a ZIP of the app bundle. No Linux or Mac player was executed, so launch behavior, data location and gameplay remain unobserved.
