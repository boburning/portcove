# OpenOMF managed Linux AppImage

The official [OpenOMF 0.8.6 release](https://github.com/omf2097/openomf/releases/tag/0.8.6), source `e389b0b5f96c9eda5f2894cacd19202952cdc8a3`, supplies x86-64 asset `467381991` at 29,170,168 bytes. The AppImage matches the publisher SHA-256 `1b57f564b2823dad0c5bdcb6c09dd5e57d286c8afa9ba99a351bf0b3939f56df`. The type-2 AppImage contains an in-image `AppRun -> usr/bin/openomf` link, an x86-64 player, SDL2, the freeware game resources and the distribution's own mods. The package remains intact. The selector accepts the stable versioned x86-64 AppImage and excludes other archive formats and architectures.

[Tagged profile and resource lookup](https://github.com/omf2097/openomf/blob/e389b0b5f96c9eda5f2894cacd19202952cdc8a3/src/resources/resource_paths.c) checks the explicit OpenOMF overrides, then the corresponding XDG values for state and configuration, then SDL's OpenOMF preference path. The archive's SDL library identifies Ubuntu SDL 2.30.0. [The corresponding SDL resolver](https://github.com/libsdl-org/SDL/blob/release-2.30.0/src/filesystem/unix/SDL_sysfilesystem.c#L272) uses `XDG_DATA_HOME/OpenOMF` or `HOME/.local/share/OpenOMF`. [OpenOMF's writer coordinates](https://github.com/omf2097/openomf/blob/e389b0b5f96c9eda5f2894cacd19202952cdc8a3/src/resources/resource_files.c) keep `openomf.conf` in configuration and `openomf.log`, `SCORES.DAT`, `screenshot`, `rec`, `save` and `mods` in state. The separate system mod path follows the selected resource root.

Core checks the actual absolute profile locations and the specific writer leaves, refuses managed path overlap and unsafe aliases, and leaves existing user files in place. The managed route requires its bundled resources. It holds when an earlier upstream resource search location would win or a custom OpenOMF override is present. The upstream separate-copy route preserves those layouts. The AppImage needs the host's normal AppImage support. The player ELF declares glibc 2.34. Its directly required bundled SDL2 library declares glibc 2.38, the highest observed requirement across 60 inspected ELF members. The existing Windows executable, selectors and player-owned external profile retain their creating contract. The stable Apple silicon package still needs its upstream setup and Homebrew library versions. The self-contained Mac app was observed on the separate rolling release.

[The tagged path type](https://github.com/omf2097/openomf/blob/e389b0b5f96c9eda5f2894cacd19202952cdc8a3/src/utils/path.h#L22) holds 256 bytes including the terminator. The launch guard checks the original and resolved resource search bases, the known profile filenames and state descendants, and reserves room under the AppImage mount for the runtime name and resource descendants. The exact archive's longest relative resource path is 61 bytes.

The [SDLPal Linux AppImage](https://github.com/sdlpal/sdlpal/releases/tag/v3.0.2025.0616), asset `264188592`, matched publisher SHA-256 `089796f9eddc032da280505fd2a2aca5f9f4d823a84499eb7693064d123dc5fe`. Its wrapper changes to the mounted `usr/bin` and executes the player. Its setup can change the actual game/save and log paths while running. The OpenOMF environment-based guard does not cover those writers. Keep SDLPal's upstream setup until the Linux managed route can protect those selected data and write destinations.

The package checks used static archive and tagged-source inspection. Portcove's controlled tests cover selector, profile and alias behavior. Native gameplay, a populated profile, FUSE availability and protected publication require separate evidence.
