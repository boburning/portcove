# Historical Windows support anchors for successor preview

This evidence crosswalk covers the 57 catalog IDs with matching legacy
Windows x86-64 automated and manual fields at source revision
`9674eaf92f3d5338b10318f9bae0454eb9161fcf`. The catalog SHA-256 is
`99e68184a771e7412a87e7ad505b03ccf87e8b11f45c59bf5faba2b21f322624`.
The catalog and live issue and Project owners retain their existing roles.

All 57 canonical issues from the dated [source-provenance inventory](../archive/2026-09-06-supported-source-provenance-audit.md)
have a retained September 4 Windows owner receipt. Seven had earlier manual
evidence. [PR #231](https://github.com/boburning/portcove/pull/231) recorded four
additional results, and [PR #232](https://github.com/boburning/portcove/pull/232)
recorded the other 46. Exact membership comes from the catalog before and after
`a366ea315b86cfe5a7a8f3cc867612b0ebed7732` and
`5f2efeff05a1453c6012aa5fdbccf94cf8f8c1ff`. Every canonical issue and its complete
comment page were read, using only these 57 issue numbers. [Issue #16](https://github.com/boburning/portcove/issues/16)
corroborates the four-title handoff and 57-port inventory. The owner receipts
cover the defined Windows gameplay, graphics and audio, controls, and save/load
checks in their recorded scope. Preserve those observations without repeating them.

## Exact joins and remaining gaps

- **One qualified artifact identified.** [Final Fantasy VII #76](https://github.com/boburning/portcove/issues/76)
  explicitly names Windows v0.1.6 and SHA-256
  `27ba89d86434b398afda80baf3e3f8b29e3347a59cf96079a4be175723bff3cd` as
  the qualified artifact. It records the original USA three-disc normalized
  track identities, the immutable three-pair runtime set and 2,207-file verify,
  `Final_Fantasy_7.exe --no-launcher`, and persistent memory cards. The owner
  receipt and #231 preserve the corresponding Windows hands-on result.
  A complete setup/working-directory/arguments/data fingerprint and reviewed
  lifecycle-check version, including any required version-transition check,
  still need reconstruction before using this as a successor-policy anchor.
- **Three exact historical automation artifact identities.** The recorded
  [OpenGOAL campaign](../archive/2026-09-03-deferred-campaign.md#opengoal-retail-source-and-windows-lifecycle-qualification)
  matches the Windows v0.3.5 adopted ZIP SHA-256
  `5b808c0db78eddb4f7a2a15fb57a74b79014a448563680d12cb22e997abb995d`
  and v0.3.6 managed ZIP SHA-256
  `98aa727f10414faa0d60c233827f472d057150f56baf85506858592d39656cb0`.
  Each title had a distinct retail source, generated application tree and data
  boundary. Its owner attestation follows the campaign and names Windows and
  the individual title. The attestation does not identify which package bytes
  the owner used, so the exact automation package cannot stand in for that join.
- **Three further version-and-source joins.** [PR #176](https://github.com/boburning/portcove/pull/176)
  records Gen2Recomped v0.7.35 integrity, installation and title-screen launch
  for each separate Gold, Silver and Crystal source. The canonical issues bind
  distinct normalized source SHA-1s. None of those retained receipts names the
  v0.7.35 package SHA-256. Later package digests in the issues date from
  separate observations and cannot fill that gap.
- **All other rows retain their Windows owner credit and platform automation
  credit.** A named historical automated release, where recovered from the
  [qualification history snapshot](https://github.com/boburning/portcove/blob/5f2efeff05a1453c6012aa5fdbccf94cf8f8c1ff/docs/archive/2026-09-03-catalog-qualification-history.md)
  or [deferred campaign](../archive/2026-09-03-deferred-campaign.md), is recorded
  below. An empty ref means the bounded evidence did not join a specific
  automation ref. It does not erase the underlying result. Later archive
  inspections, source hashes, helper executable hashes, rolling tags without a
  saved digest, and checked-in release selectors cannot establish the tested
  package bytes. A same-release automation run does not prove a version transition.

## Approval decision

The preview covers only three enforced dynamic game-source contracts across
six platform and contract rows. None of the 57 legacy Windows IDs intersects
that pilot. The current catalog declares GitHub or GitLab release providers for
356 operational ports across 705 platform declarations, including all 57 legacy
IDs. These are provider declarations. Fixed assets, built outputs, channel
restrictions, and exact selector availability require separate Core evaluation.

The proposed owner decision is to allow independently verified historical owner
and automated receipts to anchor an inherited claim at the same exact platform,
release bytes, source variant, representation, route and reviewed check version.
That permits crediting an old qualified package without repeating the original
human observations. Each successor still needs exact separate admission,
integrity, matching Core setup/launch/data coordinates and a passing automated
lifecycle receipt. Withhold activation until those joins and an actual successor
fixture are verified by the protected producer. The bounded crosswalk contains
one explicitly identified historical qualified artifact and no complete
first activation case. No other claim or existing support tier changes.
