# Catalog policy

The embedded catalog is curated, versioned data. It is not a directory of every decompilation project.

## Admission rules

A V1 candidate must be in the approved `V1-CUTOFF.md` queue and:

- have an active public upstream, or a thoughtfully reviewed retired upstream with an immutable checksum-pinned final artifact;
- produce a runnable PC build or a straightforward portable release;
- have a deterministic source requirement and launch boundary;
- fit an existing adapter without running arbitrary project scripts;
- separate application files from user data well enough for safe update and rollback;
- identify supported platforms honestly, even when that is Windows only;
- publish a verifiable SHA-256 digest or checksum sidecar before automated installation can succeed.

Active GitHub and GitLab entries are checked against live upstream state. A hosted repository that becomes archived stops resolving new updates. A deliberately retired entry must use the `retired` status and a stable direct manifest that pins one artifact per declared platform by URL, byte size, and SHA-256. Superseded and abandoned projects remain rejected.

## Channels and tiers

- `stable`: normal tagged, non-prerelease releases.
- `beta`: opt-in prereleases or projects still completing qualification. Common prerelease tag suffixes such as `-dev`, `-alpha`, `-beta`, and `-rc` are honored even when an upstream GitHub release omits the prerelease flag.
- `rolling`: opt-in named continuous-build tags.

Channel choice is per port and defaults to stable when available. Update policy is separate: notify, download/stage, or automatic activation.

## Initial research set

The current 61-port catalog includes the HarbourMasters family (Ship of Harkinian, 2Ship2Harkinian, SpaghettiKart, Ghostship, Starship, and Lighthouse), Dusklight, Zelda 64: Recompiled, Banjo: Recompiled, Quest 64: Recompiled, the six-port AKI wrestling recompilation family, several other focused N64 recomp projects, re:Blue, all 15 PS1 projects in the current RetComM catalog, Space Station Silicon Valley: Recompiled, Animal Crossing PC Port, Project Picori, BattleShip, F-Zero X G-Diffuser, Severed Chains, OpenPete, the three OpenGOAL games, Mega Man X6 Recompiled, Paper Mario ReCut, and a small opt-in beta/rolling set. Platform declarations are allowed to be narrower than the overall app's Windows/Linux/macOS support.

The approved V1 research boundary and remaining game queue are frozen in `V1-CUTOFF.md`. Repository discovery can improve evidence for that queue but cannot silently expand it.

This list is a qualification queue as well as product data. Repository activity alone is not enough: release assets, checksum publication, source variants, executable detection, save locations, and clean rollback must be verified per platform before a port is considered release-ready. Missing checksums fail closed rather than silently downgrading integrity.

Qualification evidence is platform-specific and separate from release channels and support tiers. `automated_tested_platforms` records completed install, verify, release-resolution, and launch-window automation. `manually_validated_platforms` is a stricter subset for observed gameplay, audio, controls, and save/load behavior. The 15 PS1 entries use RetComM as a discovery catalog only. Each Portcove release points directly to the same per-game GitHub repository named by the corresponding RetComM title entry. `TechnicallyComputers/RetComM-Launcher` is forbidden as a game release source in catalog validation, and `scripts/check-retcomm-upstreams.mjs` compares every mapped PS1 entry with the live RetComM catalog in CI. The shared, independently checksum-pinned `TechnicallyComputers/retcomm-toolchains` package is build infrastructure rather than a game or launcher dependency.

PS1 source profiles accept CHD storage while validating the normalized Track 01 content identity published by each game upstream. The CHD's own storage hash is recorded separately. A single-disc game takes one `.chd`; a multi-disc profile takes a directory containing exactly the declared number of `.chd` files, sorted by filename and then matched to the declared disc identities in order. Bomberman Party Edition, Bomberman World, Klonoa, Legend of Mana, Marvel vs. Capcom, the 17-track Masters of Teräs Käsi, Metal Slug X, and Rampage Through Time completed checksum-qualified builds, exact registered-source rechecks, verified manifests, and responsive launches without adapter changes. The first cutoff expansion wave added reusable source materializations. N64 sources can be byte-order normalized, ordinary exact sources can be copied or extracted from a single-member ZIP, GameCube ISO/GCM/RVZ/CISO/GCZ/WIA sources can be normalized to ISO through a locally supplied DolphinTool, and single-disc PS1 CHDs can be transactionally expanded to a multi-BIN/CUE runtime directory through local `chdman`. Source records retain both normalized content identity and original container identity. On Windows, Animal Crossing PC Port, Project Picori, and BattleShip completed checksum-qualified install and responsive-process smoke checks. Space Station Silicon Valley: Recompiled installed and launched responsively, but its upstream first-run picker still needs manual source selection, so automation evidence is not claimed.

File-set profiles register one folder or ZIP containing a declared set of top-level files. Every required member has an exact filename allowlist and an upstream-published SHA-1, SHA-256, and/or CRC32 identity; the combined content record changes if any member changes, while ZIP storage identity is retained separately. Runtime targets may transactionally copy those members from either storage form or N64-normalize folder members into separate managed paths. G-Diffuser is the first catalog consumer. Cannonball qualification proved the ZIP/CRC32 route against all 31 files in the exact local OutRun Revision B set, but Cannonball itself remains uncataloged until its application release publishes verifiable integrity.

Multi-disc PS1 profiles may use per-disc upstream volume IDs when upstream identifies retail discs by their ISO 9660 identity instead of publishing full-image hashes. Portcove still records both normalized and original-container SHA-256 identities locally, requires filename-sorted CHDs with exact track counts, and checks every extracted data track. The `psx-raw-set` materializer transactionally expands the registered set to `disc-01.bin`, `disc-02.bin`, and so on without retaining intermediate cue files or audio tracks. Severed Chains is the first consumer. Rolling releases derive their managed version from both the mutable tag and the verified artifact digest so a republished tag remains updateable.

OpenGOAL uses the `upstream-validated-disc` source kind and `ps2-iso` materializer. Registration accepts a user-owned ISO or CHD and records its container identity; it does not pretend that a container hash is a retail-revision allowlist. During first setup, Portcove transactionally copies an ISO or converts a CHD with local `chdman`, then invokes only the fixed catalog arguments of the checksum-verified OpenGOAL extractor. That pinned upstream validator must succeed and create the declared per-game marker before Portcove launches `gk`. A failed setup never writes the successful-launch marker.

The high-value second wave deliberately reused existing contracts. Mega Man X6 Recompiled uses the single-disc `psx-bin-cue` materializer with the upstream-published Rev 1 Track 01 identities and fixed `--game`, `--bios`, and `--disc` arguments. Its v1.0.9 Windows package installed and verified at 560 files; the exact RomM CHD normalized to the required 599,985,792-byte data track, launched a responsive named window, collected 300 cache/mod/save/config files after a graceful exit, and restored them after remove/reinstall. Paper Mario ReCut is an opt-in Windows beta using the upstream Paper Mario decomp's US SHA-1, the prerelease's fixed nested runtime, and its documented `user/pm.n64.us.z64` location. Its v0.1.2 package installed and verified at 75 files, skipped the picker with the staged exact ROM, launched responsively, collected the complete release-local `user` directory, and restored all 59 collected files after remove/reinstall. Both releases also passed isolated adoption, verification, source staging, responsive launch, persistence collection on removal, and byte-for-byte original-tree preservation. Failed-download cleanup is enforced by the shared installer regression test. Neither port claims the full automation badge until a second compatible release permits update/rollback qualification and hands-on checks are completed.

## Adding or changing a port

1. Confirm the title is in `V1-CUTOFF.md`, then confirm that upstream and license/distribution terms allow managing its application artifacts.
2. Inspect recent releases, asset names, prerelease flags, rolling tags, and checksums.
3. Add precise platform asset hints and executable hints.
4. Define the narrowest correct source profile and persistent paths. Set `runtime_source_filename` only to a safe relative path when upstream documents or implements a stable stored-source location. Choose the reviewed materialization explicitly when it is not the N64 default. Use `runtime_subdirectory` only for a stable nested release layout, and keep every persistent path relative to the managed install root.
5. Run the catalog/unit/CLI checks and the live repository audit. For a RetComM-discovered PS1 entry, also add its title mapping to `scripts/retcomm-psx-upstreams.json` and run `node scripts/check-retcomm-upstreams.mjs`; this audit reference never replaces the direct game release repository.
6. Add a platform to `automated_tested_platforms` only after fresh install, failed download recovery, verify, update, rollback, remove, adoption, and launch-window checks pass there.
7. Add it to `manually_validated_platforms` only after a person observes gameplay, audio, controls, and save/load behavior on that platform.
8. If implementation or qualification stops, add or update the per-game row in `docs/DEFERRED.md`, including missing or mismatched source revisions, absent checksums/releases, runtime failures, and researched candidates that were not admitted to the catalog.

Never add copyrighted source hashes casually. Accepted SHA-1, SHA-256, or CRC32 values must come from documented upstream requirements and identify only the user-supplied source variant; Portcove never distributes that source. A runtime-managed local copy remains user-supplied data and must be included in persistence and removal boundaries.
