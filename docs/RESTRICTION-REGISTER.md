# Restriction register

This register lists the limits found in Portcove and what should happen to each.
It records the location, scope and class of each limit, its rationale, what a
player or pipeline sees at the limit, which callers depend on it, a proposed
disposition and the validation evidence. It serves the arbitrary-limits work
under #1422. Each mechanism pull request changes code and adds its own
`## Restriction register rows`. This register is the shared inventory that
those rows update. It changes no product behavior.

Every row was observed at commit `47f824704` (`main`, after #8606). Line numbers
refer to that commit. A row is evidence about that commit, not a live status;
mechanism pull requests own the changes and their acceptance.

## How to read this register

Owner direction: "Library growth, provider growth, accumulated history, and
temporary resource pressure must not make supported work permanently unusable."
Every retained limit needs a concrete purpose and one of these classes:

| Class   | Meaning                                                                          | What the row must name                      |
| ------- | -------------------------------------------------------------------------------- | ------------------------------------------- |
| 1       | Actual external provider, runtime, filesystem or format constraint               | The provider, OS or format fact             |
| 2       | Integrity, identity, ownership or containment requirement                        | The property protected                      |
| 3       | Resource budget for a bounded unit of work                                       | The unit and its continuation               |
| 4       | Accidental ceiling on supported content, library size, history or workflow scope | Removed by the owning mechanism             |
| UNKNOWN | Not established                                                                  | The measurement or decision that settles it |

"A page size, cache capacity, or processing batch with functioning continuation
is not automatically a product defect. Follow its actual callers and failure
behavior." A continuation counts only when a production caller persists and
consumes it. Where a class-3 row says no production caller consumes its
continuation, the budget is an effective ceiling. Its disposition says so.

Session labels name the open mechanism session that owns the area. These
labels come from the lead's assignment map. At the time of writing, none of
these branches had been pushed.

row was confirmed in that session's own inventory. Each mechanism pull request
confirms its rows.

### Method

The sweep covered Core (`crates/portcove-core`), the CLI, Tauri
(`apps/desktop/src-tauri`), React (`apps/desktop/src`),
`portcove-release-tools`, `portcove-listing-carrier` and `scripts/`. A read-only
pattern sweep of production code (test modules and test files excluded) found
1,303 candidate lines:

- named `MAX`, `LIMIT`, `BOUND`, `CAP` and `BUDGET` constants;
- `.take(N)` and `.slice(0, N)` calls;
- SQL `LIMIT`;
- `per_page` and page sizes;
- `Duration` literals and timeout fields;
- retry and attempt counts.

Each area was then traced by hand from producer to every consumer. That tracing
covered literal comparisons that refuse, truncate or stop paging. It also
covered archive envelopes and the non-numeric restrictions the owner named:

- guide length;
- title-specific branches;
- enumerated release qualifications;
- save-format and per-engine capability;
- optional evidence that became a universal gate;
- repeated whole-inventory work.

A pattern hit is a candidate, not a finding. Rows record only limits whose
behavior was traced. When more than one area reached the same site, the rows
were merged into one: DL-04 into PV-21, CD-08 into DL-08, CD-09 into DL-11,
DK-11 into LC-11, SC-29 into LC-14 and LC-16, SC-30 into LC-15, AR-13 into
MD-02, MD-03 into AR-12, and PV-19 into MD-15. Those Ids are retired. Ids are
not renumbered.

The pattern sweep is not a repository command. A Node test would need
registration in `.github/workflows/ci.yml`, which is outside this register's
scope. Re-run the sweep with `rg` over the patterns above when refreshing a row.

  - SC-22: the selected original folder is walked again on every preparation.
- **Providers (L3):** GitLab `resolve` reads the whole release history each time
  (PV-09). Each "show older" step in the release chooser re-reads from page 1
  (PV-08).

  source in one 30 s batch, with no partial result or hash reuse (DL-21).
- **Publication history (L6):** each publication-inventory reader restarts its
  scans (PH-05). History verification reads every retained listing body.

## D. Unassigned work

The work below is not covered by any open session. Entries are ranked by
player and pipeline impact. Each scope is meant to start one session. Rows that
belong to a session but need the lead to confirm the assignment come last.

1. **Guide-length bound blocks registration routes (SR-01, SR-03, DM-30; SR-02 is GR).**
   - Where: Core caps steps plus references at 8 and warnings at 8
     (`catalog.rs:1179-1180`, `catalog/listings.rs:975-976`). Authoring
     (`scripts/catalog-authoring.mts:313`) and route facts
     (`scripts/catalog-route-facts.mts:194-199`) mirror the cap.
   - Effect: 24 ports and 46 listings are already at 8. 94 authored listings
     could not take the two generated steps, so their otherwise usable routes are
     withheld as `guide-bound`.
   - Scope: replace the count with a byte envelope per guide (class 3), or with
     a collapsible guide structure that released readers accept.
   - Producer and consumers: update authoring, route facts, generated
     registration and the listing projection together.
   - Checks: Core validation accepts what publication emits. Released-reader
     compatibility is checked against the LD minimum preview.
2. **Host preferences document is one 64 KiB record (LC-13, also SC-24).**
   - Contents: favorites, hidden, saved and followed IDs, collections,
     recommendations and the 8 DAT references all live in one document
     (`host_preferences.rs:16`).
   - Effect: library growth eventually refuses every preference write,
     including locale and library root.
   - Scope: move per-library organization and DAT references into the library
     store as rows, with a forward migration of the existing document. Keep a
     small bounded document only for true host settings.
3. **Browsing and game-file responses have whole-library ceilings (DK-02, DK-03, DK-04).**
   - Where: the browsing projection, capped at 8,192 contexts and 4 MiB per
     response, with 16 MiB serialized (`browsing_context.rs`); the registered
     source and game-file snapshot responses, capped at 4 MiB

   - Effect: context filters show "unavailable" for the whole library, and the
     game-file refresh is refused once a library is large enough.
   - Retained facts: these get a fixed 250 ms per refresh in a fixed order, so
     later ports are never observed.

     facts; page the game-file query.
   - Note: this overlaps DL-21 (L5) on the source-hash batch.
4. **Add to Library refuses selections above 512 with no chunking (LC-10, DK-12, LC-11).**
