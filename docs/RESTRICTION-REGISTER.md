# Restriction register

This register lists the limits found in Portcove and what should happen to each.
It records the location, scope and class of each limit, its rationale, what a
player or pipeline sees at the limit, which callers depend on it, a proposed
disposition and the validation evidence. It serves the arbitrary-limits work
under #1422. Each mechanism pull request changes code and adds its own
`## Restriction register rows`. This register is the shared inventory that
those rows update. It changes no product behavior.

"Restriction" here means any limit on content, size, history, time or workflow.
It is unrelated to the catalog's typed acquisition restrictions (download holds)
in [CATALOG.md](CATALOG.md).

Rows were traced at commit `47f824704` and re-pinned to `e53fee315` (`main`
after #8618 and #8622). Locations cite each limit by file and by the name of the
constant, function or literal that holds it. Other cells may still quote a line
number; those refer to `47f824704`. A row is evidence about that commit, not a
live status. Mechanism pull requests own the changes and their acceptance.

## How to read this register

Owner direction: "Library growth, provider growth, accumulated history, and
temporary resource pressure must not make supported work permanently unusable."
Every retained limit needs a concrete purpose and one of these classes:

| Class   | Meaning                                                                          | What the row must name                                                                              |
| ------- | -------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| 1       | Actual external provider, runtime, filesystem or format constraint               | The provider, OS or format fact. An application's own format or compatibility choice is not class 1 |
| 2       | Integrity, identity, ownership or containment requirement                        | The property protected                                                                              |
| 3       | Resource budget for a bounded unit of work                                       | The unit and its working continuation                                                               |
| 4       | Accidental ceiling on supported content, library size, history or workflow scope | Removed by the owning mechanism                                                                     |
| UNKNOWN | Not established                                                                  | The measurement or decision that settles it                                                         |

"A page size, cache capacity, or processing batch with functioning continuation
is not automatically a product defect. Follow its actual callers and failure
behavior." A continuation counts only when a production caller persists and
consumes it. A budget whose continuation no production caller consumes is an
effective ceiling and is class 4. Its rationale starts with "Effective ceiling".

### Sessions

### Method

The sweep covered Core (`crates/portcove-core`), the CLI, Tauri
(`apps/desktop/src-tauri`), React (`apps/desktop/src`),
`portcove-release-tools`, `portcove-listing-carrier` and `scripts/`. A pattern
sweep of production code (test modules and test files excluded) found 1,303
candidate lines:

- named `MAX`, `LIMIT`, `BOUND`, `CAP` and `BUDGET` constants;
- `.take(N)` and `.slice(0, N)` calls;
- SQL `LIMIT`;
- `per_page` and page sizes;
- `Duration` literals and timeout fields;
- retry and attempt counts.

Each area was then traced by hand from producer to every consumer. That tracing
covered literal comparisons that refuse, truncate or stop paging. It also
covered archive envelopes and the non-numeric restrictions the owner named:

- guide length;
- title-specific branches;
- enumerated release qualifications;
- save-format and per-engine capability;
- optional evidence that became a universal gate;
- repeated whole-inventory work.

A pattern hit is a candidate, not a finding. Section B records limits whose
behavior was traced. [Appendix F](#f-other-named-bounds) classifies every other
named production bound constant more briefly.

When more than one area reached the same site, the rows were merged into one:

### Ratchet

`scripts/check-document-links.test.mts` keeps the register current:

- Every Location must name an existing file.
- Each name cited after a file must still occur in that file.
- Every production constant whose name has a `MAX`, `MAXIMUM`, `LIMIT`,
  `BOUND`, `CAP` or `BUDGET` segment must be named in section B or appendix F,
  or listed in the test's reviewed exclusions.

A renamed or new bound therefore fails CI until its row is updated.

### Expensive whole-inventory work in the register's areas

- **Lifecycle:**
  - `metadata_snapshot` serializes every profile revision, retained history,
    membership and artwork record. It runs on each metadata export, library move
    plan and recovery-bundle plan, and twice per bundle creation.
  - `add_games_to_library` rescans pending setups once per request.
- **Scans:**
  - SC-08: pruning re-checks the same oldest 20,000 observations after every
    scan.
  - SC-17: full store detection runs on every move check.
  - SC-22: the selected original folder is walked again on every preparation.
- **Providers:** GitLab resolution reads the whole release history each time
  (PV-09). Each "show older" step in the release chooser re-reads from page 1
  (PV-08).
- **Catalog distribution:** definition acquisition downloads every content
  target on each refresh, with no digest reuse (DL-08). The definition snapshot
  is serialized whole into one SQLite column (CD-05).
- **Deadlines:** the browsing game-file refresh hashes every registered source
  in one 30 s batch (DL-21).
- **Publication history:** each publication-inventory reader restarts its scans
  (PH-05). History verification reads every retained listing body.
