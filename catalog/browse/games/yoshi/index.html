Setup

  1. Prepare a permitted completed cycle player

    Use an already permitted noncommercial source-built Yoshi Windows cycle player under the selected title/framework PolyForm Noncommercial terms and applicable component notices; the shared UI has separate MIT terms. Complete upstream generation/build outside Portcove in a separate folder. This handoff is not a package/component attestation, does not grant original-game or optional media rights, and does not establish a legacy or HD executable as the cycle product.

  2. Keep the supported original and backend together

    Use your own current supported USA Yoshi payload: CRC32 E7EAD93B, 128 KiB PRG plus 32 KiB CHR. The documented canonical NES 2.0 file SHA-1 is 71cc02d4a005c6ad71f1fbf2b3ccd890d65056a3. Upstream accepts the older header declaring 64 KiB CHR only for the complete known payload and length; this is not acceptance of arbitrary truncation, revisions or regions. The previous larger input and its states are a separate unqualified contract.

  3. Select the completed native player and actual configuration

    Select the already working completed cycle YoshiRecomp.exe, using its containing runtime folder as working directory for normal defaults. Preserve an already working custom working directory and the interpretation of existing path arguments instead of changing them merely to register. Do not choose setup.bat, setup.sh, a compiler, headless tool or another backend executable. Use one literal argument token: the absolute path to your supported ROM, with spaces kept inside that token. The ordinary upstream launcher remains available; these cycle builds do not accept the SNES --rom or --no-launcher flags. Preserve an established --config and its absolute path as separate tokens when already used; do not switch configuration merely to register.

  4. Review launch details, then choose Play

    Review and consent to the exact native executable, working directory and literal arguments. Registration does not compile, migrate, repair or launch the game. Choose Play separately; upstream’s ordinary launcher and game loop are in-process in the selected source. Portcove observes the selected process, not an exclusive process family. Relink an upstream replacement through a new review and close every actual player before upstream changes.

  5. Keep your working copy and use the project’s updates

    Preserve the whole creating runtime/source tree, original, config.ini and any custom configuration, its rom.cfg, older keybinds.ini, mods, cycle states under saves/<ROM stem>.cycstate, diagnostics/captures and all custom paths. Yoshi has no battery-backed save, but that does not make its cycle states disposable. Legacy binary states and states from the previous larger ROM are not qualified for this cycle/input; keep each with its creating copy. Do not rename or import old files merely to register. Upstream/player own preparation, repair and runtime replacement. Removing registration removes only Portcove metadata and preserves all external bytes.

Limitations and evidence

  • Default settings use executable-parent config.ini; rom.cfg follows the chosen settings file. A custom --config is not an all-writes redirect: default cartridge battery/state paths remain executable-relative. Preserve actual existing --save-file choices; do not add --save-file or --no-save merely to register. --no-save disables battery loading as well as writing.
  • These upstream previews and their source/backend migration reports are not Portcove gameplay or save-compatibility qualification. Core user-selected registration does not authenticate the ROM, generated code, component rights or build provenance. No managed acquisition/setup/Install/Update/Backup/Rollback/migration/external deletion, sandbox, network/debug/netplay or exclusive process-family guarantee is supplied. Actual game execution, gameplay/state/installed/protected and other-platform observations remain unqualified here.
