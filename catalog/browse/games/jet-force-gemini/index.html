Setup

  1. Check the required game files

    Use your own USA z64 ROM, SHA-1 493ced9008dbe932d6e91179b68e8630cf23a023.

  2. Start the complete portable package

    Extract the v1.3.2 portable archive into a writable folder. On Windows 10 or 11 with Direct3D 12, open JetForceGeminiRecompiled.exe. For the Linux x64 tarball and AppImage, use glibc 2.35 or newer, Vulkan and system FreeType and D-Bus libraries. For the tarball, open JetForceGeminiRecompiled from the extracted folder. Choose your own ROM in the launcher.

  3. Use the prepared Linux copy

    For the prepared portable tarball, select JetForceGeminiRecompiled as the executable and its containing folder as the working directory. Choose Play when you want to start that external copy. The .exe in the next step is for Windows.

  4. Select the prepared player

    Select JetForceGeminiRecompiled.exe and use its containing folder as the working directory. Leave arguments empty. Keep the complete independently permitted runtime and finish the title-specific preparation before Play.

Setup notes
Choose the Linux package and keep its data
The portable tarball keeps data beside its executable. The AppImage runs from a writable copy in JFG_GAME_DIR, or in JetForceGeminiRecompiled under XDG_DATA_HOME (default ~/.local/share). Keep saves, settings, mods and texture_packs in the folder you actually use. For Steam Deck, start the AppImage through Steam.
Replace a Linux 1.2.x copy
Use the current upstream release page for the first update after the repository rename. Keep a backup of your portable folder or AppImage data before replacing it. The 1.3.2 release fixes an upstream Linux crash when selecting a save after restart.
Registration ownership and removal
Portcove records the selected executable, working folder and literal arguments after review. Play is separate and only the selected process is supervised. You and upstream own replacement and updates; relink changed executable bytes after reviewing them. Removing this registration preserves every external file. Managed installation, backup, rollback, migration and deletion are not offered for this external copy.
Player-data ownership
You and upstream own the external copy's data: the portable executable’s containing folder, including saves, settings, mods and texture packs. Back up these locations separately; registration does not migrate or certify their compatibility.

Limitations and evidence

  • The Windows upstream updater can replace and restart the executable. End the Portcove Play session before using that updater from the standalone player. Keep the data of other Jet Force Gemini implementations separate.

Setup

  1. Prepare the exact supported N64 original

    Use a complete player/components you are independently permitted to use, with your own Jet Force Gemini US big-endian .z64 ROM: 33,554,432 bytes, SHA1 493ced9008dbe932d6e91179b68e8630cf23a023. The released importer checks the whole file and stores its verified copy as roms/jfg-us.z64 under the selected profile. Other regions, modified originals and byte-swapped files are not admitted by this route. Finish Select ROM and normal profile/settings preparation upstream; keep the independent original. No ROM, converter, helper, compiler or game is obtained or executed here.

  2. Keep the complete prebuilt Windows release

    The inspected official 1.4.0 Windows x64 ZIP contains AMD64 JFG-Launcher.exe and jfg-native-boot.exe, matching libraries/notices and jfg-package.json binding the native runtime. The launcher carries its own embedded setup/helper and stages it in profile data; a missing loose JFG-Setup.exe in this package is not evidence that the native runtime must be built by the player. The released player needs no Git, Python, Visual Studio or developer compilation. Maintainer-only generated/oracle inputs remain outside this public player route and are not accessed or represented as reproducible from this guide.

  3. Add the prepared normal launcher

    Select JFG-Launcher.exe, use its complete extracted player directory as working directory and leave arguments empty. Review the intent and request Play separately, then use its normal Play action with the prepared profile. Source keeps the native frontend and supervised session handle while the game runs; it is not a short-lived compiler wrapper. Keep the matching native runtime/helper/resources together. Do not select the bare jfg-native-boot.exe with its default finite probe, add private child flags, diagnostic replays or developer scene selectors as normal Play. End the actual game normally, then close the returning launcher to finish the session.

  4. Preserve profiles, copied ROMs and storage selection

    Normally keep %LOCALAPPDATA%/JFGRecomp with profiles/default and any selected profiles, verified roms/, native profile/configuration, saves, controller-pak data, settings, shader caches and helper/support data. Game > Settings can choose another storage directory, copying existing profile data without overwriting destination files, then restarting the launcher. Existing portable.txt/userdata and storage-location.txt affect that selection. Keep the actual active root, the locator beside the launcher, old roots, originals and recovery together when moving/updating. Cartridge saves and controller paks are different objects; this guide performs no import, migration, backup, restore or deletion.

  5. Check what the game and its components support

    Retain project MIT, N64Recomp/runtime, RT64, RmlUi/FreeType, fonts and all shipped component notices; these do not license the original Rare/Nintendo game or third-party mods. The dependency inventory explicitly excludes the unqualified RecompFrontend entry pending permission; it is not a grant or the current native UI’s admission. Upstream campaign verification used testing mods/unlocked state, and modern controls/high-refresh/device feel retain limitations. Quit normally, keep recovery and review/relink changed bytes after upstream replacement. No native/installed, ordinary campaign, real-save, physical-device, supported excluded component or Supported acceptance is asserted. Registration removal preserves external files; managed lifecycle operations remain unavailable.

Limitations and evidence

  • Keep the prebuilt launcher/runtime unit, exact imported US ROM, profiles and storage-location.txt. Do not attach a finite-probe default or infer campaign/device acceptance from upstream testing mods.
