Setup

  1. Preserve the exact game original and separate BIOS

    Use your own unchanged Pokémon Emerald USA GBA original, SHA-1 f3ae088181bf583e55daf962a92bb46f4f1d07b7, and your own retail GBA system BIOS, 16384 bytes, SHA-1 300c20df6731a33952ded8c436f7f186d25d3492. The BIOS is a separate required input even though the short game quick-start omits it. No BIOS or game original is supplied or downloaded by these instructions. Keep originals unchanged outside the new player folder and use matching private copies in a separate writable folder before upstream preparation; do not select the original archive as a writable save location. Other revisions, patched games, other regions or another Pokémon game are different inputs. Do not override an upstream mismatch warning or infer that a warning authenticates a file.

  2. Finish upstream setup and select this game player

    Open the linked official v0.1.3 release and extract its complete EmeraldRecomp-windows-x64-v0.1.3.zip package into a separate writable folder for this exact game. Keep EmeraldRecomp.exe, DLLs, assets, mods and overlay_toolchain companions together. Finish normal upstream BIOS/ROM selection using the matching private copies, then register the already working EmeraldRecomp.exe with its containing folder as working directory and preserve its already working literal arguments. The packaged tcc.exe and i386-win32-tcc.exe are compiler helpers, not game players. Keep the upstream PolyForm Noncommercial and dependency/attribution notices. These are in-development previews despite the release metadata flag; a package version is not gameplay qualification.

  3. Keep the data and compiler paths

    Before explicit Play, preserve the complete creating runtime and its actual data locations. The launcher writes config.ini/keybinds.ini and BIOS/ROM path caches; the runtime also has bios.cfg/rom.cfg sidecars. Default battery data sits beside the selected ROM as .sav, with .sav.tmp and .sav.prev-size.bak witnesses; save states use .state<N>, .suspend.state and .suspend.pending beside that ROM. Existing --save or --state-dir arguments change those coordinates: preserve their actual destinations and do not rewrite them through this guide. Generated reports and recomp_cache/JIT executable output belong to upstream; keep the full working player folder and actual ROM/data folder, not just the EXE or one save file. Close every game/compiler process before copying or replacing files. Do not share these folders between titles, transplant emulator/PokePort/another engine saves or states, or infer compatibility between builds.

  4. Use the upstream Linux AppImage

    Choose EmeraldRecomp-linux-x86_64 from the upstream releases page. The observed v0.1.5 player needs glibc 2.34 and libstdc++ providing GLIBCXX_3.4.30. Open it with the host’s AppImage support and use its own ROM and BIOS picker. Its launcher uses ~/.local/share/EmeraldRecomp by default, or EmeraldRecomp under XDG_DATA_HOME when set. EMERALDRECOMP_HOME overrides the complete path. Different AppImages can share that writable home. Back up that whole profile, the original files, and actual save and state locations before replacing the app.

  5. Import the separate ROM and BIOS in the Android app

    Use the official Android ARM64 APK. The observed v0.1.5 package requires Android 9 or later. In its setup screen choose your own USA Pokémon Emerald ROM and 16 KiB retail GBA BIOS separately. The app validates and copies them into its private roms and bios folders. Keep your original files separately. The app keeps its battery save under its private saves folder, and clearing app data or uninstalling can remove that save. Use a same-signed in-place update if you need to retain the app’s data and keep the creating version until you have verified actual recovery.

  6. Register the prepared player and use explicit Play

    You manage this external game, original files, compiler outputs and saved data. The project’s tools generate native game code and replace caches; Portcove does not take over those files. It saves the executable, working folder and launch arguments you select; choose Play explicitly when you are ready. Removing the registration leaves external files in place. Portcove does not offer updates, backups, rollback, data migration or external-file deletion for this copy. Finish first-time setup with the project’s tools. These instructions do not confirm successful original-game setup, gameplay, multiplayer, saving and loading or physical controls.

Limitations and evidence

  • Select your prepared game in Portcove, review its launch details, then choose Play. The automated process check did not run this game or use its original files.
  • Portcove-managed installation is not offered for this route. Support would require separate checks of this game’s original files, BIOS, generated code, saved data and update behavior. Do not import existing data or assume it is compatible with another Pokémon implementation.
  • Linux and Android use their own upstream setup and replacement. The Android release disables Android backup in its manifest. The ROM and BIOS copies are not a backup of the app’s private saves.

Setup

  1. Use this exact original game

    Use your own canonical US English emerald original: revision 1.0, 16 MiB, SHA-1 f3ae088181bf583e55daf962a92bb46f4f1d07b7. Another game, region or unlisted revision is a different input. The upstream importer checks SHA-1; Portcove registration does not authenticate the original or cache.

  2. Complete the upstream import and select this player

    Use only the official bryanthaboi/gen1recomp release or gen1re.com distribution. Extract the complete Windows ZIP and keep gen1recomp.exe with its supplied companions. Run upstream setup deliberately, then select this game’s plain original .gb or .gba file in its importer. Completing import may start the game automatically; this is an explicit upstream launch, not a passive Portcove file check. Let import finish and verify this game’s tab before registration. Register gen1recomp.exe in gen1recomp-win64 with that containing directory as working directory and one literal argument, --game=emerald. Do not select another game’s cache or a console/emulator/helper.

  3. Set up on Linux, Mac or Android

    On Linux x86-64, make the official AppImage executable and select it with its containing folder. On Intel or Apple Silicon Mac, keep the extracted gen1recomp.app intact. Select its Contents/MacOS/love executable and the Contents/MacOS folder. First import the matching original using the upstream player. In Portcove, review one argument, --game=emerald, before saving the registration. Use Play to start it. Flatpak and Android players use upstream setup and launch. On Linux without FUSE, add --appimage-extract-and-run before --game=emerald as its own argument.

  4. Add the game and manage updates

    The standalone upstream player owns its update checks and can mount an updated Lua payload from the OS profile. Let upstream own that complete installation and profile. This entry uses non-owning registration, explicit Play and registration-only removal; Managed Update, Backup, Rollback, migration and external deletion are unavailable. It does not use or alter Red’s separate Core-managed definition or its managed-package environment. The generated cache is private original-derived data; preserve your original outside it, and preserve any separately kept-ROM copy when offered. Use the importer’s explicit consent choices; no original is downloaded or supplied by Portcove.

Setup notes
Preserve all actual player and game data
Normal desktop data uses LÖVE’s OS user save directory with identity pokemon-love2d (normally %APPDATA%/LOVE/pokemon-love2d on Windows). portable.txt beside gen1recomp.exe redirects saves/options/generated data to that writable player folder, but updates/ payloads remain in the OS save directory. Preserve both actual locations, all imported game caches, saves/ slots and legacy save files, options and backup/staged witnesses, mods, kept original copies, imports/exports, screenshots and custom profiles. Games have distinct saves but share options and runtime. Removing the marker switches roots without moving progress. Close the player before copying/replacing anything; keep the creating runtime and originals. No automatic save/cache conversion or populated-data adoption is promised.
