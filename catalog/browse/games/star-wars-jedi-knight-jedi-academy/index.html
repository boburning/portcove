Setup

  1. Prepare matching PC game data on Windows

    On Windows, before Play, copy only assets0.pk3, assets1.pk3, assets2.pk3 and assets3.pk3 from your own patched PC GameData/base into base beside the player. Keep the original game installation unchanged and separate. The runtime also ships DLLs in base: keep them intact and copy only the four original asset archives into that folder. Jedi Academy needs its own matching files; Jedi Outcast is a different game. Portcove does not verify original-game identity. Do not copy old executables or DLLs over the official runtime. Customized game/mod layouts can retain an external registration.

  2. Keep the correct player and profile

    The managed player follows the Rolling latest build; this channel does not establish gameplay qualification. On Windows, the managed copy selects openjk_sp.x86_64.exe for single player. Multiplayer remains available by registering your separately prepared openjk.x86_64.exe copy with its actual GameData working folder; openjkded.x86_64.exe is a server. This selected Windows package contains the non-portable home-directory branch: normal saves, configuration and logs use the actual Documents/My Games/OpenJK profile. Back it up separately with your originals and creating runtime before changing versions. Portable builds, unavailable Documents folders and explicit home-path overrides can change the write location; those configurations need their own preserved external registration. A runtime rollback does not rewind external saves or establish older-runtime, mod or recorded-demo compatibility.

  3. Keep an existing prepared copy

    Extract the complete official OpenJK-windows-x86_64.zip into the prepared GameData folder. Select openjk_sp.x86_64.exe for single player or openjk.x86_64.exe for multiplayer, with GameData as working directory. A registration selects one player/mode; openjkded.x86_64.exe is a dedicated server, not the player. Retain all package libraries/resources. Existing registrations keep their selected player/mode, arguments, files and user/upstream runtime owner. Removing their registration preserves those files; this catalog change does not adopt or migrate them.

  4. Prepare the multiplayer player

    Use a separately prepared external GameData copy with the complete official Windows x64 package and your own matching assets0.pk3 through assets3.pk3 in base. Keep the package's base and OpenJK libraries intact; do not copy old game DLLs over them. Select openjk.x86_64.exe with that GameData folder as working directory, not the single-player executable or dedicated server. This player also needs a compatible Microsoft Visual C++ v14 x64 runtime; the x86 runtime alone is insufficient. For the documented software-audio route, enter +set, s_UseOpenAL and 0 on three separate argument lines. Each line is one literal argument. The bundled legacy OpenAL/EAX DLLs are 32-bit and are not x64 dependencies for this route.

  5. Choose one installation route

    A library can have only one installation or registration for this title at a time. Choose managed single player or a separately prepared external player; do not register files inside a Portcove-managed installation or output folder. Preserve your originals, complete external profile and creating runtime before changing routes, then use the existing removal choice first. Registration-only removal preserves all external files. The external multiplayer route offers reviewed registration, separate Play and preserving registration removal, not managed installation, updates, backup, rollback, migration or deletion of that copy. Existing managed single-player installations and retained registrations keep their own contracts.

  6. Prepare the upstream Mac player

    Unpack the official OpenJK Mac tarball for your Mac with the system archive tools. Keep the app and its required game data in the matching Jedi Academy GameData layout. Open openjk_sp.arm64.app or openjk_sp.x86_64.app for the campaign. Use openjk.arm64.app or openjk.x86_64.app for multiplayer. Keep the complete app, including libSDL2-2.0.0.dylib in Contents/Frameworks and follow the project’s data setup instructions. The inspected packages require macOS 14 or later on Intel and macOS 15 or later on Apple Silicon.

  7. Prepare the Linux OpenJK campaign profile

    Put the original archives in $XDG_DATA_HOME/openjk/base when XDG_DATA_HOME is set to an absolute path. Otherwise, with XDG_DATA_HOME unset, use ~/.local/share/openjk/base. Use only assets0.pk3 through assets3.pk3 from your own patched PC GameData/base. The inspected official build requires glibc 2.34, libstdc++ with GLIBCXX_3.4.29, SDL2, zlib, libjpeg.so.8, libpng16.so.16 and libOpenGL.so.0.

Setup notes
Keep multiplayer profiles and downloads
Preserve the complete actual OpenJK profile, including base and each mod's directory, openjk.cfg, logs, screenshots, recorded demos and server-downloaded packages or unfinished downloads. The selected non-portable Windows build normally uses Documents/My Games/OpenJK; fs_homepath overrides, portable builds or an unavailable Documents folder can change the location. Keep the external working GameData copy and its originals too. Upstream or you replace this multiplayer runtime. Server downloads and mods are not Portcove-managed runtime updates, and existing demos, mods, saves or server compatibility are not guaranteed after replacement. Preserve the actual Linux OpenJK profile at $XDG_DATA_HOME/openjk or ~/.local/share/openjk, or ~/Library/Application Support/OpenJK on Mac. Keep any explicit fs_homepath, original data, mods and the creating runtime. The upstream apps can share a profile location.

Limitations and evidence

  • Keep the external working GameData copy and its originals too. Upstream or you replace this multiplayer runtime. Server downloads and mods are not Portcove-managed runtime updates, and existing demos, mods, saves or server compatibility are not guaranteed after replacement.
  • Keep the Unix profile and original archives outside the Portcove library and back them up separately. Use a separately prepared copy for profiles with alternate native modules. Managed runtime replacement and rollback leave this external data in place.
