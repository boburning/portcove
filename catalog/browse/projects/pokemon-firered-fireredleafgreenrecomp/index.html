Setup

  1. Preserve the exact game original and separate BIOS

    Use your own unchanged Pokémon FireRed USA v1.0/rev0 GBA original, SHA-1 41cb23d8dccc8ebd7c649cd8fbb58eeace6e2fdc, and your own retail GBA system BIOS, 16384 bytes, SHA-1 300c20df6731a33952ded8c436f7f186d25d3492. The BIOS is a separate required input even though the short game quick-start omits it. No BIOS or game original is supplied or downloaded by these instructions. Keep originals unchanged outside the new player folder and use matching private copies in a separate writable folder before upstream preparation; do not select the original archive as a writable save location. Other revisions, patched games, other regions or another Pokémon game are different inputs. Do not override an upstream mismatch warning or infer that a warning authenticates a file.

  2. Choose a managed or prepared copy

    Install the official Windows package through Portcove, then choose Play to select your matching original and BIOS in the game’s picker. To prepare a copy yourself, extract the complete FireRedRecomp Windows x64 ZIP and finish upstream ROM and BIOS setup before registering FireRedRecomp.exe with its containing folder as the working directory. Keep any working launch arguments. Keep the libraries, assets, mods and compiler companions together.

  3. Keep the data and compiler paths

    Before explicit Play, preserve the complete creating runtime and its actual data locations. The launcher writes config.ini/keybinds.ini and BIOS/ROM path caches; the runtime also has bios.cfg/rom.cfg sidecars. Default battery data sits beside the selected ROM as .sav, with .sav.tmp and .sav.prev-size.bak witnesses; save states use .state<N>, .suspend.state and .suspend.pending beside that ROM. Existing --save or --state-dir arguments change those coordinates: preserve their actual destinations and do not rewrite them through this guide. Generated reports and recomp_cache/JIT executable output belong to upstream; keep the full working player folder and actual ROM/data folder, not just the EXE or one save file. Close every game/compiler process before copying or replacing files. Do not share these folders between titles, transplant emulator/PokePort/another engine saves or states, or infer compatibility between builds.

  4. Register the prepared player and use explicit Play

    You manage this external game, original files, compiler outputs and saved data. The project’s tools generate native game code and replace caches; Portcove does not take over those files. It saves the executable, working folder and launch arguments you select; choose Play explicitly when you are ready. Removing the registration leaves external files in place. Portcove does not offer updates, backups, rollback, data migration or external-file deletion for this copy. Finish first-time setup with the project’s tools. These instructions do not confirm successful original-game setup, gameplay, multiplayer, saving and loading or physical controls.

Setup notes
Updates, backups and rollback
Portcove updates its managed Windows copy and carries declared local settings, input pointers, game.toml, local saves and complete versioned mods. Generated compiler output stays with the runtime that created it. Originals, BIOS and default saves or states beside the selected game are outside Portcove backups. Runtime rollback carries current declared data and does not rewind saves. An external copy stays under your control.

Limitations and evidence

  • Select your prepared game in Portcove, review its launch details, then choose Play. The automated process check did not run this game or use its original files.
  • The upstream code uses PolyForm Noncommercial 1.0.0. Keep the component notices and use your own game and BIOS. Do not assume saves or states work with another implementation or an older runtime.
