Setup

  1. Prepare the correct PS4 game and update upstream

    Use a complete copy and components you are independently permitted to use. The 0.4 Windows route documents your own CTR Nitro-Fueled PS4 CUSA13795 or CUSA14876 base game and matching 1.21 update; both documented 1.21 firmware builds are accepted by upstream. Follow its first setup outside Portcove and keep independent originals before creating its merged game folder. Its preparation uses hard links where possible: a merged tree is not an independent backup of original file contents. No original, DLC, extractor, Python helper or game is obtained or executed here.

  2. Keep the complete selected Windows implementation

    The inspected CTR-NitroFueled-PC-portable-windows.zip contains CTR-NitroFueled-PC-portable/CTR-NitroFueled-PC.exe, bin/sacredfire.exe, bundled python, scripts, DLLs and resources. The ordinary frontend is an AMD64 native Windows launcher, not the older Python launcher or a standalone game exe. Keep the whole matching package. This is the existing GetLostIn Windows adaptation of SacredFire with its own maintained Windows layer/launcher and credited upstream fixes; a common game title does not merge it with the separate online fork or qualify the parent’s Linux route.

  3. Select and retain the normal launcher session

    After upstream setup, select CTR-NitroFueled-PC.exe, use its complete extracted portable package directory as working directory and leave arguments empty. Review and consent to the selected launch details, then choose Play separately. This opens the upstream launcher; request its Play only when ready. The native frontend waits for its Python runner, which waits for sacredfire.exe. The runner loops over its own Apply and restart exit code, retaining the ordinary waiting chain. Quit the actual game before closing the frontend; its Stop game and quit action forcibly terminates the job and is not a save-flush guarantee. Portcove has not tested this launch-and-quit sequence.

  4. Preserve the actual data and hard-link sources

    Keep the whole package user tree with savedata, cache and trophies, the separate backups and DLC directories, launcher.ini, bbport.ini, patches.json, logs and the full prepared game view. Keep the original base/update/DLC sources independently too. The runner normally uses user for saves/cache, while an established BB_USER_DIR or other data/mod/config override can select additional external roots; preserve every effective location. Do not edit a hard-linked merged source as though it were an isolated disposable copy. This guide performs no save import, migration, backup or deletion.

  5. Leave replacement and recovery with upstream

    Complete upstream updates, first preparation, repairs and source-root changes outside an attached session. Close all actual players/helpers before replacing files, keep independent recovery copies, then review/relink changed executable bytes. Normal waiting/restart source paths do not establish observed forced-stop cleanup or save consistency. Portcove does not own the mutable upstream runtime, merged originals, backups or external player data. Removing registration preserves all external files.

  6. Retain permission and platform limits

    Preserve GPL 2-or-later and all packaged third-party/NVIDIA/font notices; these grants do not grant original-game or DLC rights. Upstream playable race/audio/controller/save reports remain upstream claims; shader stalls and experimental upscaling/frame-generation/ultrawide limits remain. This guide does not establish Portcove gameplay, multiplayer, save/reload, installed-app or Supported acceptance. No managed install/update/rollback/backup/removal is offered.
